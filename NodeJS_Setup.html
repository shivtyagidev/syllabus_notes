PHASE 1 — Node.js Fundamentals

Node.js kya hai?

  • Node.js na language hai, na framework — yeh ek Runtime Environment hai.
  • Yeh JavaScript ko server-side pe execute karne deta hai (browser ke bahar).
  • Node.js C++ mein likha gaya hai aur andar se Google ka V8 engine use karta hai.

Runtime Environment kya hota hai?

  • Woh environment jo code ko execute karne ki power deta hai — memory manage karta hai, I/O handle karta hai.
  • Framework sirf development simplify karta hai; Runtime Environment actual execution karta hai.
Real-life analogy JavaScript = electricity (current). Browser = ghar ka socket (client side outlet). Node.js = server ka socket (server side outlet). Bina socket ke electricity useless hai — Node.js JavaScript ko server pe "plug in" karta hai.

Interview Trap Q: "Is Node.js a programming language?" — ❌ No. It is a runtime environment. JS is the language; Node.js is the environment that runs it on the server.

V8 Engine kya hai?

  • V8 Google ka open-source JavaScript engine hai, originally Chrome browser ke liye banaya gaya.
  • Yeh JavaScript code ko seedha machine code mein convert karta hai — interpret nahi karta, compile karta hai (JIT — Just In Time Compilation).
  • Isliye JavaScript bahut fast run hoti hai.

Interview Trap Q: "V8 aur Node.js same hai?" — ❌ No. V8 sirf execution engine hai. Node.js = V8 + libuv + Node APIs + npm. Browser bhi V8 use karta hai, lekin Node.js V8 ko server environment mein use karta hai.

When to USE Node.js:

  • REST APIs, microservices
  • Real-time apps — chat, gaming, live notifications
  • I/O-heavy apps — file upload, DB operations, API calls
  • Streaming apps — video/audio streaming

When NOT to use Node.js:

  • CPU-intensive tasks — image/video processing, heavy encryption, ML
  • Reason: Single main thread block ho jaata hai CPU-heavy kaam se
Real-world use cases Netflix (streaming) • LinkedIn (API server) • Uber (real-time location) • PayPal (REST APIs) • WhatsApp (messaging)
Interview Trap Q: "Node.js CPU-intensive kaam bilkul nahi kar sakta?" — ❌ Wrong. Kar sakta hai via worker_threads ya separate microservice, lekin yeh default best fit nahi hai. Honest answer: "I/O-bound ke liye best hai; CPU-bound ke liye worker_threads ya alag service use karo."

Key Components — Interview mein yahi poochha jaata hai
  • V8 Engine — JS ko machine code mein convert (JIT compile)
  • Call Stack — function execution track karta hai, LIFO (Last In First Out)
  • libuv — Node ka C++ async library; Event Loop aur Thread Pool dono issi ke andar hain
  • Thread Pool — default 4 threads; file I/O, crypto, DNS, zlib yahan handle hota hai
  • Event Loop — "koi callback ready hai?" continuously check karta hai; single-threaded hai
  • Microtask Queue — process.nextTick + Promises; Event Loop phases se pehle chalta hai
  • Macrotask Queue — setTimeout, setImmediate, I/O callbacks; Event Loop phases mein chalta hai

Single-Threaded kya hota hai?

  • Sirf 1 main thread hota hai jo JavaScript execute karta hai.
  • Ek time pe sirf ek JS operation run ho sakti hai.
  • Yeh "limitation" nahi — yeh design choice hai: thread management ka overhead khatam.
Single Thread:
Main Thread (T1)
   → Task1 complete karo
   → Task2 complete karo
   → Task3 complete karo
(ek ke baad ek, lekin I/O ke liye rukta nahi)

Multi-Threaded kya hota hai?

  • Multiple threads parallel mein kaam karte hain.
  • Risk: Deadlock (do threads ek hi resource lock kar lein), Race Conditions.
  • CPU-intensive kaam ke liye better suited.
Multi Thread:
T1 → Task1
T2 → Task2   ← parallel
T3 → Task3   ← parallel
T4 → Task4   ← parallel
(fast, lekin coordination complexity zyada)
🔥 Interview Trap — Node.js COMPLETELY single-threaded nahi hai

❌ Wrong: "Node.js mein sirf ek thread hai."

✅ Right: "Node.js JavaScript ek single main thread pe execute karta hai. Lekin libuv ka Thread Pool background mein 4 threads use karta hai heavy I/O operations ke liye (file system, crypto, DNS)."

libuv Thread Pool:

  • Default: 4 threads (UV_THREADPOOL_SIZE se badha sakte ho, max 128)
  • Kab use hota hai: fs operations, crypto, DNS lookup, zlib compression
  • DB queries aur network calls Thread Pool use nahi karte — woh OS-level async hote hain
Main Thread (JS)

      ├── fs.readFile   → libuv Thread Pool ← yahan Thread Pool use hota hai
      └── crypto.pbkdf2 → libuv Thread Pool ← yahan bhi

Worker Threads kya hote hain?

  • Node.js ka built-in module hai: worker_threads
  • CPU-heavy JavaScript code ko alag thread pe run karne deta hai
  • Main thread block nahi hota
const { Worker } = require('worker_threads');

// Heavy CPU work alag thread pe
const worker = new Worker('./heavy-calc.js');
worker.on('message', (result) => console.log('Result:', result));

// Main thread free rehta hai
console.log('Main thread free hai!');

PHASE 2 — Event Loop & Async Node.js

Synchronous (Blocking): Ek task pura hone tak dusra shuru nahi hota. Main thread RUK jaata hai.

Task 1 (10s) → Task 2 (8s) → Task 3 (4s) → Task 4 (5s)
Total = 27s ❌  (sum of all)
// BLOCKING — thread ruka rahega
const data = fs.readFileSync('file.txt', 'utf8');
console.log(data);        // file read hone ke baad hi chala
console.log('Done');      // is ke baad chala

Asynchronous (Non-Blocking): Task shuru karo, rukna mat — callback/Promise se result baad mein lo.

Task 1 start ──┐
Task 2 start ──┤  (sabhi saath shuru)
Task 3 start ──┤
Task 4 start ──┘
Total = 10s ✅  (longest task ka time)
// NON-BLOCKING — thread nahi rukta
fs.readFile('file.txt', 'utf8', (err, data) => {
  console.log(data);    // file ready hone pe callback fire hoga
});
console.log('Done');    // yeh PEHLE chalega

Interview Trap

Q: "Asynchronous matlab parallel hai?" — ❌ No. Parallel = multiple threads pe same time. Async = ek thread pe, lekin I/O ka wait nahi karta. Node.js async hai lekin single-threaded bhi hai.

Q: "Sync vs Single-threaded same hai kya?" — ❌ No. Single-threaded = worker ki count. Sync = execution order. Node.js single-threaded + async dono hai.

Call Stack kya hota hai?

  • Yeh ek stack (LIFO) data structure hai jo function execution track karta hai.
  • Jab function call hota hai → stack pe push hota hai. Jab return hota hai → pop hota hai.
  • Sirf ek function ek time pe top pe hota hai — yahi "single-threaded" ka matlab hai.
function greet() { console.log('Hello'); }
function main() { greet(); }
main();

// Call Stack:
// [main] → push
// [main, greet] → push
// [main] → greet returns, pop
// [] → main returns, pop

Event Loop kya karta hai?

  • Continuously check karta hai: "Call Stack khaali hai?"
  • Agar khaali hai → Queue se callback uthata hai → Stack mein dalta hai → execute hota hai.
  • Yahi Node.js ko async banata hai — Event Loop kabhi rukta nahi (jab tak process hai).
EVENT LOOP (loop chalta rehta hai):
  while (true) {
    if (callStack.isEmpty()) {
      if (nextTickQueue.hasItems())   → execute all nextTick
      if (promiseQueue.hasItems())    → execute all promises
      if (timerQueue.isReady())       → execute timers
      if (ioCallbackQueue.hasItems()) → execute I/O callbacks
      if (checkQueue.hasItems())      → execute setImmediate
    }
  }

🔥 Important Clarification — Common Misconception

Call Stack se async kaam directly Queue mein nahi jaata.

Actual flow yeh hai:

  1. Call Stack pe async operation shuru hota hai (e.g., fs.readFile() call)
  2. Woh operation libuv / OS ko de diya jaata hai — Call Stack se hata diya jaata hai
  3. libuv background mein kaam karta hai (Thread Pool ya OS async I/O)
  4. Jab operation complete hota hai, uska callback/continuation uske type ke anusar schedule hota hai:
    • process.nextTick() → Next Tick Queue
    • Promise.then() / async/await → Microtask Queue
    • setTimeout / setInterval → Timers Phase (Event Loop)
    • fs.readFile / DB / network → Poll Phase (Event Loop)
    • setImmediate → Check Phase (Event Loop)
  5. Event Loop yeh queues/phases check karta hai aur callback ko Call Stack pe push karta hai
  6. JavaScript Call Stack pe execute hoti hai
Call Stack
    |

    |                        kaam complete hua
    |                               |
    |                    type check karo:
    |                    I/O callback → Poll Phase queue
    |
Event Loop (Poll Phase)
    |

    |
Call Stack → Execute callback

process.nextTick — Dangerous tool

process.nextTick() Event Loop se pehle fire hota hai. Agar recursively call karo:

process.nextTick(function loop() {
  process.nextTick(loop); // ⚠️ Event Loop kabhi aage nahi badhega!
});

Isliye production mein nextTick ko carefully use karo — sirf current operation ke ek step baad run karna ho tab.

Rule yaad karo:

1. Synchronous code     (Call Stack — sabse pehle)
2. process.nextTick()   (Microtask — priority 1)
3. Promise.then()       (Microtask — priority 2)
4. setTimeout()         (Event Loop — Timers Phase)
5. I/O Callbacks        (Event Loop — Poll Phase)
6. setImmediate()       (Event Loop — Check Phase)

Callback kya hai? Ek function jo kisi doosre function ko argument ke roop mein diya jaata hai, aur baad mein call kiya jaata hai.

function fetchData(callback) {
  setTimeout(() => {
    callback(null, { user: 'Shiva' }); // null = no error
  }, 1000);
}

fetchData((err, data) => {
  if (err) return console.log('Error:', err);
  console.log('Data:', data); // { user: 'Shiva' }
});

Error-first Callback (Node.js convention):

  • Pehla argument hamesha error hota hai (null agar koi error nahi)
  • Dusra argument result/data hota hai
  • Yeh Node.js ka standard pattern hai: (err, data) => {}
fs.readFile('file.txt', 'utf8', (err, data) => {
  if (err) return console.log('Error:', err);  // error pehle check karo
  console.log(data);
});

Multiple Promises — 4 Methods (Detail):

1. Promise.all()

Sabhi Promises successful hone ka wait karo. Ek bhi fail hua → poora Promise.all() reject.

const p1 = Promise.resolve("User");
const p2 = Promise.resolve("Profile");
const p3 = Promise.resolve("Posts");

Promise.all([p1, p2, p3])
  .then(result => console.log(result))   // ["User", "Profile", "Posts"]
  .catch(error => console.log(error));

Agar ek fail ho:

const p1 = Promise.resolve("User");
const p2 = Promise.reject("Profile API Failed");
const p3 = Promise.resolve("Posts");

Promise.all([p1, p2, p3])
  .then(result => console.log(result))
  .catch(error => console.log(error));   // "Profile API Failed"
Promise.all() Flow 
p1 ——————— SUCCESS ——  ┬
p2 ———— FAIL —————┼—→ Promise.all → REJECT
p3 ————————— SUCCESS ┘

Real-life example: Dashboard ko 3 APIs chahiye (User + Profile + Orders). Teeno required hain → use Promise.all().

Interview line: Promise.all waits for all promises to resolve and rejects immediately when any promise rejects.

2. Promise.allSettled()

Sabhi Promises ka result chahiye, chahe success ho ya failure. Ek fail hone ke baad bhi poora process fail nahi hota.

const p1 = Promise.resolve("User");
const p2 = Promise.reject("Profile Failed");
const p3 = Promise.resolve("Posts");

Promise.allSettled([p1, p2, p3])
  .then(results => console.log(results));

// Output:
// [
//   { status: "fulfilled", value: "User" },
//   { status: "rejected",  reason: "Profile Failed" },
//   { status: "fulfilled", value: "Posts" }
// ]
Promise.allSettled() Flow 
p1 —— SUCCESS ———— ┬
p2 —— FAIL —————┼—→ allSettled → ALL RESULTS
p3 —— SUCCESS ————┘

Real-life example: Admin dashboard mein User count + Revenue + Notifications + Orders — aapko har API ka result chahiye (pass ya fail). → Promise.allSettled().

Interview line: Promise.allSettled waits for all promises to complete and returns the status and result of each promise, whether fulfilled or rejected.

3. Promise.race()

Jo Promise sabse pehle settle ho — success OR failure — uska result milega. Settled = fulfilled OR rejected.

const p1 = new Promise(resolve => setTimeout(() => resolve("API 1"), 3000));
const p2 = new Promise(resolve => setTimeout(() => resolve("API 2"), 1000));
const p3 = new Promise(resolve => setTimeout(() => resolve("API 3"), 2000));

Promise.race([p1, p2, p3])
  .then(result => console.log(result));  // "API 2"  (1 sec fastest)

Agar fastest reject hua:

const p1 = new Promise(resolve => setTimeout(() => resolve("Success"), 3000));
const p2 = new Promise((_, reject) => setTimeout(() => reject("Failed"), 1000));

Promise.race([p1, p2])
  .then(r => console.log(r))
  .catch(e => console.log(e));   // "Failed"  ← p2 first settled (rejected)

Real-life example: API ko maximum 2 seconds wait karna hai → race against a timeout:

const apiCall = fetch("/api/users");
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject("Request Timeout"), 2000)
);

Promise.race([apiCall, timeout])
  .then(result => console.log(result))
  .catch(error => console.log(error));

Interview line: Promise.race settles with the first promise that settles, whether it fulfills or rejects.

4. Promise.any()

Jo Promise sabse pehle SUCCESS kare uska result do. Failures tab tak ignore hote hain jab tak sab fail na ho jaayein.

const p1 = new Promise((_, reject) => setTimeout(() => reject("API 1 Failed"), 1000));
const p2 = new Promise(resolve  => setTimeout(() => resolve("API 2 Success"), 2000));
const p3 = new Promise(resolve  => setTimeout(() => resolve("API 3 Success"), 3000));

Promise.any([p1, p2, p3])
  .then(result => console.log(result))   // "API 2 Success"
  .catch(error => console.log(error));
// p1 fail hua (1s) → ignore
// p2 success (2s)  → WINNER

Agar sab fail ho gaye:

Promise.any([
  Promise.reject("A failed"),
  Promise.reject("B failed"),
  Promise.reject("C failed")
]).catch(error => console.log(error));   // AggregateError: All promises were rejected

Real-life example: Same service ke multiple servers hain (Server A fail, B success, C success) — kisi ek successful response se kaam chalega → Promise.any().

Interview line: Promise.any resolves with the first fulfilled promise and rejects only when all promises reject (AggregateError).

Why Modules use karte hain? (Interview Points)

  • Code Organization — bada project chhoti independent files mein break hota hai
  • Reusability — ek baar likho, kahin bhi require() karo

Module Caching

Pehli baar require() pe module execute hota hai aur cache mein store ho jaata hai. Doosri baar same module require karo → cache se milega, re-execute nahi hoga.

PHASE 5 — EventEmitter

Ek programming style jahan code events (kisi action) ke hone ka wait karta hai, aur jab wo event hota hai tab uska handler function chalta hai — upar se neeche seedha order mein chalne ke bajaye.

Node.js poora event-driven hai: request aana, file read poora hona, timer khatam hona — sab events hote hain jo apne registered listener/callback ko trigger karte hain.

Traditional vs Event-driven 
TRADITIONAL (step by step)
  Line 1 → Line 2 → Line 3 → ... (wait karo, phir agla step)

EVENT-DRIVEN (Node.js)
  Event register karo (on)  →  kaam continue karo  →  event hone pe handler chale (emit)
  Example: request aayi → 'request' event → handler function chala

EventEmitter Node.js ke built-in events module ki ek class hai jo events ko register (listen) karne aur trigger (emit) karne ka tarika deti hai. Node.js ke andar bahut saari cheezein (HTTP server, streams, process) isi class se banti hain.

Isko use karne ke 2 tarike hain — new EventEmitter() se direct object banao, ya apni class ko extends EventEmitter karke banao (jaisa niche wale example mein OrderService ke saath kiya hai).

Ek chhota sa example — isi mein neeche wale saare keywords use ho rahe hain, comments mein samjhaya gaya hai kaunsa method kya kar raha hai.

const EventEmitter = require('events');
const emitter = new EventEmitter();

function greet(name) {
  console.log('Hello', name);
}

emitter.on('greet', greet);                                  // .on() — normal listener
emitter.once('greet', () => console.log('Sirf ek baar chalega')); // .once()

emitter.emit('greet', 'Shiva');   // .emit() — custom event 'greet' trigger
// Hello Shiva
// Sirf ek baar chalega

emitter.emit('greet', 'Shiva');   // dobara emit kiya
// Hello Shiva
// (.once() wala listener is baar nahi chala, pehle hi hat gaya)

emitter.removeListener('greet', greet);  // .off('greet', greet) bhi same kaam karta hai
emitter.emit('greet', 'Shiva');          // ab kuch print nahi hoga
  • .on(eventName, cb) — listener register karta hai, har baar event emit hone pe chalega. Multiple listeners bhi laga sakte ho.
  • .emit(eventName, ...args) — saare registered listeners ko synchronously call karta hai. Koi listener na ho toh chup-chaap kuch nahi hota.
  • .once(eventName, cb) — sirf pehli baar chalega, phir khud hi remove ho jaata hai.
  • .removeListener(eventName, cb) (alias .off()) — ek specific listener hata deta hai. Reference same hona zaroori hai, isliye anonymous function ko remove nahi kar sakte — named function use karo. Saare listeners ek saath hatane ho toh .removeAllListeners(eventName).

Koi bhi string naam ek custom event ban sakta hai — Node.js mein events pre-defined nahi hote (kuch special jaise 'error' ko chhod ke), aap apni marzi ka event name choose karke .on()/.emit() se use kar sakte ho (upar wale example mein 'greet' ek custom event hai).

REST (Representational State Transfer) ek architecture style hai APIs banane ke liye jo standard HTTP methods aur URLs use karta hai resources ko access karne ke liye.

  1. Client-Server — frontend aur backend alag-alag, independently develop ho sakte hain.
  2. Stateless — server kisi client ka data requests ke beech store nahi karta.
  3. Cacheable — response mein bataya ja sakta hai ki wo cache ho sakta hai ya nahi.
  4. Uniform Interface — consistent URL/method structure (jaise /users/:id).
  5. Layered System — client ko fark nahi padta ki wo server se seedha baat kar raha hai ya kisi load balancer/proxy se.

Ek operation idempotent hai agar use 1 baar ya 100 baar call karo, server ki final state hamesha same rahe — jaise light ka switch OFF karna: 1 baar OFF karo ya 5 baar, light OFF hi rahegi, kuch aur nahi hota.

app.post('/payments', async (req, res) => {

  const existing = await redis.get(`idem:${idempotencyKey}`);
  if (existing) {
    return res.status(200).json(JSON.parse(existing)); // SAME purana response wapas do, dobara charge mat karo

Express — Types of Middleware

  1. Application-level middleware
  2. Router-level middleware
  3. Error-handling middleware
  4. Built-in middleware
  5. Third-party middleware
  • Application-level applies globally to all requests: app.use(myMiddleware).
  • Route-level applies only to specific routes: app.use('/example', middleware).

A special middleware for managing errors, defined with four parameters: (err, req, res, next). The extra err parameter is what Express uses to recognize it.

app.use((req, res, next) => {
  next(new Error("An error occurred")); // simulate error
});

app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).send("Something went wrong!");
});

The error-handling middleware should be defined last. When an error occurs, Express searches for the next error-handling middleware, skipping any regular middleware in between.

app.use(middleware1);   // 1
app.use(middleware2);   // 2 — error occurred here
app.use(middleware3);   // 3 — skipped
app.use(middleware4);   // 4 — skipped
app.use((err, req, res, next) => {   // 5 — error handler, runs
  console.error(err.stack);
  res.status(500).send("Something went wrong!");
});

// visiting /1.jpg serves the image directly from /public

  1. Unauthorized Access — anyone with DB/config access can read passwords directly.
  2. Compromise of Other Accounts — reused passwords let attackers pivot to other accounts.
  • Hashing — converts a password into a fixed-size string via a mathematical algorithm.
  • Salt — random data combined with the password before hashing. Protects even if the hacker knows the algorithm, and ensures identical passwords hash differently (each user gets a unique salt).
DiagramSalt (via bcrypt) + Hash (of plain password) are combined into the final Secure Password stored in the DB.
  1. Generate a random salt.
  2. Create a hash object using SHA-256.
  3. Update the hash object with salt + password.
  4. Get the hashed data as hex.
  5. Return salt + hashed password as a string.
const crypto = require("crypto");

function hashAndSaltPassword(password) {
  const salt = crypto.randomBytes(16).toString("hex");
  const hash = crypto.createHash("sha256");
  hash.update(salt + password);
  const hexHash = hash.digest("hex");
  return salt + "." + hexHash;
}

Node.js — Internals & Performance (5+ YOE)

  1. Timers — executes callbacks scheduled by setTimeout/setInterval.
  2. Pending callbacks — executes I/O callbacks deferred from the previous cycle.
  3. Idle, prepare — internal use only.
  4. Poll — retrieves new I/O events; executes their callbacks (this is where most work happens).
  5. Check — executes setImmediate() callbacks.
  6. Close callbacks — e.g. socket.on('close', ...).

Microtasks (Promise .then, process.nextTick) drain between every phase, not as a separate phase.

  • process.nextTick() runs before any other microtask/macrotask — right after the current operation, before the event loop continues.
  • Promise.then() microtasks run next, after all pending nextTick callbacks drain.
  • setTimeout(fn, 0) runs in the timers phase.
  • setImmediate() runs in the check phase, generally after timers on the next loop iteration (order vs. setTimeout(0) from the main module is not guaranteed, but inside an I/O callback, setImmediate always fires before setTimeout).
console.log('1');
setTimeout(() => console.log('2 - timeout'), 0);
setImmediate(() => console.log('3 - immediate'));
process.nextTick(() => console.log('4 - nextTick'));
Promise.resolve().then(() => console.log('5 - promise'));
console.log('6');
// Output: 1, 6, 4 - nextTick, 5 - promise, 2/3 (order varies at top level)

libuv is the C library that gives Node its event loop and async I/O. Network I/O is handled natively async by the OS, but some operations have no native async OS API, so libuv runs them on a Thread Pool (default size 4, configurable via UV_THREADPOOL_SIZE).

  • Uses the thread pool: fs module operations, crypto.pbkdf2/scrypt, DNS lookups (dns.lookup), some zlib compression.
  • Does not use the thread pool: network sockets/HTTP (handled by the OS kernel's async I/O directly).

Streams process data in chunks instead of loading it all into memory at once — essential for large files, video, or network data.

  • Readable — source of data, e.g. fs.createReadStream().
  • Writable — destination for data, e.g. fs.createWriteStream(), HTTP response.
  • Duplex — both readable and writable, e.g. a TCP socket.
  • Transform — a duplex stream that modifies data as it passes through, e.g. zlib.createGzip().
const fs = require('fs');
fs.createReadStream('input.txt')
  .pipe(fs.createWriteStream('output.txt'));
// streams the file in chunks instead of reading it fully into memory

Backpressure happens when a Writable stream can't consume data as fast as a Readable stream produces it — without handling it, memory usage balloons as data buffers up.

  • writable.write() returns false when its internal buffer is full — that's the backpressure signal.
  • Using .pipe() handles backpressure automatically (it pauses the readable side until the writable drains).
  • Manually, you'd listen for the 'drain' event before writing more.

Cache-aside (lazy loading): check the cache first; on a miss, query the DB and populate the cache for next time.

  • Write-through — update the cache at the same time as the DB write, always fresh but adds write latency.
  • Explicit invalidation — on update/delete, actively DEL the affected cache key(s).

Publish/Subscribe messaging — a publisher sends a message to a channel; all subscribers listening on that channel receive it instantly.

Use case: broadcasting real-time notifications across multiple Node.js instances (e.g. a chat app scaled across servers uses Redis Pub/Sub so a message from a user on server A reaches a user connected to server B).

  • RDB (snapshotting) — periodic point-in-time snapshots of the dataset to disk; compact, fast restarts, but can lose recent writes since the last snapshot.
  • AOF (Append Only File) — logs every write operation; more durable, less data loss risk, but larger files and slower restarts.
  • When the dataset is much larger than available RAM (Redis is memory-first; scaling RAM gets expensive).
  • When you need complex relational queries/joins — Redis is a key-value store, not a relational engine.
  • As the system of record for critical data without careful persistence configuration — it's usually a cache/complement to a durable DB, not a replacement.

Scenario-Based & System Design (Most repeated — startups to MNCs)

Approach to talk through:

  • Pick an algorithm: Fixed Window (simple, bursty at window edges), Sliding Window Log (accurate, memory-heavy), or Token Bucket (smooths bursts, industry favorite).
  • Store counters in Redis (via INCR + EXPIRE, or a sorted set for sliding window) so the limit is enforced correctly across multiple app instances, not per-process.
  • Key by user ID or IP; return 429 Too Many Requests with a Retry-After header when exceeded.
  1. Confirm it with metrics: watch RSS/heap trend over time (Grafana/Datadog) — steadily climbing memory that never drops after GC is the signal.
  2. Reproduce with node --inspect and take heap snapshots at intervals in Chrome DevTools; compare snapshots to see which object type is retained and growing.
  3. Check the usual suspects: unremoved event listeners, unbounded caches/arrays, uncanceled timers, closures holding large scopes.
  4. Fix, then load-test again to confirm memory stabilizes (plateaus) instead of climbing linearly.
  1. Vertical: use the cluster module or PM2 cluster mode to use all CPU cores on a box (Node itself is single-threaded per process).
  2. Horizontal: run multiple app instances/containers behind an Nginx/load balancer, and orchestrate with Kubernetes (HPA) to add/remove instances based on load.
  3. Offload the database: add Redis caching for hot reads, add read replicas for MySQL, ensure connection pooling is tuned (not one pool per instance exhausting DB max-connections).
  4. Keep the app stateless (sessions in Redis, not in-memory) so any instance can serve any request.
  5. Add a CDN for static assets, and async/queue-based processing (BullMQ/RabbitMQ) for anything that doesn't need to block the response.
  • Write path: POST /shorten {longUrl} → generate a short code (base62 encoding of an auto-increment ID, or a hash + collision check) → store {code, longUrl} in MySQL.
  • Read path: GET /:code → look up in Redis cache first (hot links are read far more than written) → fall back to MySQL on a cache miss → 301/302 redirect.
  • Scale reads with Redis + read replicas; the write path is comparatively low-volume so a single primary DB is usually enough.
  • Extras interviewers probe for: custom aliases, expiry/TTL, analytics (click counts via an async queue, not synchronously on the redirect path), collision handling.

Implement the Circuit Breaker pattern (e.g. via the opossum library):

  • Closed — requests flow normally.
  • Open — after enough failures, the breaker "trips" and fails fast (returns an error or fallback immediately) without calling the failing service, for a cool-down period — this stops your own service from piling up slow/hanging requests and running out of resources.
  • Half-Open — after the cool-down, it lets a trial request through; if it succeeds, the breaker closes again.

Pair with timeouts on every outbound call and a sensible fallback (cached/default data) where possible.

  • Pessimistic locking — SELECT ... FOR UPDATE inside a transaction locks the row until commit, forcing the second request to wait.
  • Optimistic locking — add a version column; update with WHERE id = ? AND version = ?, and if 0 rows are affected, someone else updated it first — retry.
  • For simple counters, use an atomic operation instead of read-then-write, e.g. UPDATE items SET stock = stock - 1 WHERE id = ? AND stock > 0 (or Redis DECR), rather than reading the value in app code and writing it back.

Client sends a unique Idempotency-Key header with each payment request (generated once per user action, reused on retries).

  • Server checks if that key already exists (in Redis or a DB table) before processing.
  • If it exists and the original request already completed, return the stored result immediately without re-charging.
  • If it's in-flight, reject/wait rather than processing concurrently.
  • Store the key with a reasonable TTL (e.g. 24h) since retries typically happen soon after the original attempt.
  • Don't send notifications synchronously inside the request that triggers them — push a job onto a queue (RabbitMQ/BullMQ on Redis/Kafka) and return immediately.
  • Separate worker processes consume the queue and call the actual provider (SendGrid, Twilio, FCM).
  • Add retries with backoff for transient provider failures, and a dead-letter queue for messages that repeatedly fail.
  • Make sends idempotent (dedupe key) so a retried job doesn't double-notify the user.
  • On Kubernetes: a rolling update with a properly configured readiness probe (see Ch.22) does this automatically.
  • Without K8s: run behind Nginx/a load balancer with multiple instances, deploy one at a time, remove it from rotation, update, health-check, add it back, repeat (a manual "rolling" deploy) — or use PM2's reload which restarts cluster workers one at a time.
  • Always keep DB migrations backward-compatible during the rollout window (old and new app code must both work against the schema mid-deploy).
  • URI versioning — /api/v1/users, /api/v2/users (most common, simple, explicit).
  • Header versioning — e.g. Accept: application/vnd.myapp.v2+json (keeps URLs clean).
  • Keep old versions running (deprecate with a sunset date/header) until clients migrate; never silently change a response shape on an existing version.
  • MySQL (relational) — data has clear relationships, needs transactions/ACID guarantees, complex joins/reporting — e.g. orders, payments, inventory.
  • MongoDB (document) — data is naturally hierarchical/variable-shaped, schema evolves often, horizontal scale matters more than joins — e.g. product catalogs with varying attributes, activity logs, content management.

Good answer style: pick based on the access pattern and consistency needs of that specific feature, not a blanket preference — many real systems use both ("polyglot persistence").

  • Centralize authentication in one Auth Service that issues signed JWTs after login.
  • Other services verify the JWT signature locally (stateless) instead of calling the Auth service on every request — avoids a hot dependency/bottleneck.
  • Use short-lived access tokens + longer-lived refresh tokens; refresh happens through the Auth service, access-token verification doesn't.
  • An API Gateway can handle token verification once at the edge before routing to internal services.

Node.js Fundamentals — Deep Dive

Only your JavaScript code runs on a single thread (the main thread/event loop). Node delegates I/O work (network calls, file reads, DB queries) to the OS kernel's async APIs or libuv's thread pool, and the main thread is never blocked waiting for them.

So thousands of requests can be "in flight" simultaneously — each one's I/O is happening in the background, and the single thread just keeps picking up completed work from the event loop's queue and running the (fast, non-blocking) JS callback for it. This works great for I/O-heavy workloads, but a single CPU-heavy synchronous task still blocks everyone else.

A global object giving information about, and control over, the current Node.js process — available everywhere without require().

  • Node also exposes module-specific globals that don't exist in browsers: __dirname, __filename, require, module, exports.
  • Blocking — execution waits for an operation to finish before moving to the next line; the event loop is stuck, nothing else can run.
  • Non-blocking — the operation is handed off (to the OS/thread pool), execution continues immediately, and a callback runs later when it completes.

  1. The OS accepts the TCP connection and hands it to libuv, which notifies the event loop.
  2. Node's HTTP parser reads the raw request and constructs the req/res objects.
  3. Express's middleware stack runs in order (logging, auth, body-parsing, etc.), each calling next().
  4. The matched route handler runs; if it needs I/O (DB query, external API), that work is delegated (thread pool / OS async) and the main thread is freed to handle other requests in the meantime.
  5. When the I/O completes, its callback is queued and the event loop picks it up, resuming the handler and calling res.send()/res.json().
  6. The response is written back to the socket.

Since there's only one thread running JS, a heavy synchronous computation (e.g. a huge loop, synchronous image resizing, JSON.parse on a massive payload) blocks the entire event loop — every other request, timer, and I/O callback has to wait until it finishes. This is a classic way to accidentally tank throughput for all users, not just the one who triggered it.

Fix: move CPU-bound work off the main thread — use worker_threads, offload to a separate service/queue, or break the work into smaller async chunks.

Async JS — Call Stack, Promises & Combinators

The Call Stack is where JS tracks function calls currently executing — each call pushes a frame on, and returning pops it off (LIFO). The event loop only pulls the next callback from the queue once the call stack is empty.

A stack overflow happens when calls pile up faster than they return — classically from unbounded recursion with no base case.

function recurse() {
  return recurse(); // no base case — RangeError: Maximum call stack size exceeded
}

Real-life analogy: a stack of plates — you can only take the top plate off (return from the most recent call) and you can only add a new plate on top (make a new call). You can't reach into the middle.

Often asked as: "Why does a long synchronous loop delay a setTimeout(fn, 0) callback?" — because the timer callback can't run until the call stack is empty, and a busy loop keeps the stack (or at least the main thread) occupied the whole time.

async/awaitSyntactic sugar over Promises — lets async code read like synchronous code, easiest to reason about

Real-life analogy: a callback is like telling a friend "call me when the pizza arrives" (you passed them your own phone number to use); a Promise is a receipt/tracking number you can check or hand to someone else; async/await is reading that tracking status as if it updated instantly, without the mental overhead of "wait, whose callback am I in right now?"

Interview trap: async/await doesn't replace Promises — it's built entirely on top of them (see next card). Every async function still returns a Promise under the hood.

A Promise has exactly 3 states:

  • Pending — initial state, neither fulfilled nor rejected yet.
  • Fulfilled — the operation completed successfully (resolve(value) was called).
  • Rejected — the operation failed (reject(error) was called).
const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve('done'), 1000); // pending â†’ fulfilled after 1s
});

Once a Promise moves to fulfilled or rejected, it's settled — it can never change state again, and calling resolve()/reject() a second time is silently ignored.

Real-life analogy: a sealed exam result envelope — once opened and read as "pass" or "fail", it can't later flip to the other outcome. It's locked in.

An async function always returns a Promise. Inside it, await pauses execution of that function (without blocking the event loop) until the awaited Promise settles, then resumes with the resolved value — or throws if it rejects (catchable with try/catch).

async function getUser(id) {
  const user = await db.query('SELECT * FROM users WHERE id = ?', [id]);
  // execution pauses here, event loop keeps handling other work,
  // resumes once the query Promise resolves
  return user;
}

Under the hood it's built on generators + Promises — the engine effectively resumes the function each time the microtask queue processes the awaited Promise's resolution.

Real-life analogy: it's like pausing a recipe at "simmer for 20 minutes" — you (the function) step away and do something else, but you come back and continue from exactly that line once the timer's done, rather than standing at the stove doing nothing.

Often asked as: "Does await block the event loop?" — No. It only pauses the current async function's execution; the event loop is completely free to handle other requests/timers/I/O while waiting.

Plain await has no built-in timeout — it waits forever unless the underlying call itself times out. Race it against a timer using Promise.race():

  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('Operation timed out')), ms)
  );
  return Promise.race([promise, timeout]);
}

Retry with backoff — retry a few times with an increasing delay, instead of hammering a struggling service immediately:

async function withRetry(fn, retries = 3, delay = 500) {
  for (let attempt = 1; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === retries) throw err;
      await new Promise((r) => setTimeout(r, delay * attempt)); // 500ms, 1000ms, 1500ms...
    }
  }
}

Often asked as: "Why exponential/increasing backoff instead of retrying immediately?" — immediate retries against an already-struggling service can make the overload worse (a "retry storm"); backing off gives it room to recover.

Deeply nested callbacks (each depending on the previous one's result) form a "pyramid of doom" — hard to read, hard to handle errors consistently.

// Callback hell

  getOrders(user.id, (err, orders) => {
    getInvoice(orders[0].id, (err, invoice) => {
      // ...deeper and deeper
    });
  });
});

// Flattened with async/await
const user = await getUser(id);
const orders = await getOrders(user.id);
const invoice = await getInvoice(orders[0].id);

Real-life analogy: a phone tree where each menu option says "press 1, then wait, then from the new menu press 2, then wait, then from that menu press 3..." — nestled deeper and deeper, each step obscured inside the previous one. async/await is like getting a direct extension number for the whole path instead.

Often asked as: "What specifically makes callback hell bad, beyond just how it looks?" — error handling gets duplicated/inconsistent at every level (each callback needs its own error check), and it's very easy to forget one, silently swallowing an error deep in the nesting.

Authentication & Authorization — Deep Dive

  • Access token — short-lived (e.g. 15 min), sent on every API request, verified statelessly. If leaked, the damage window is small.
  • Refresh token — long-lived (e.g. 7-30 days), stored more carefully (httpOnly cookie), used only to obtain a new access token from a dedicated /refresh endpoint. Can be revoked server-side (stored in DB/Redis, unlike a stateless access token).

This gives you the performance of stateless verification on every request, while still keeping a way to force logout/revoke access.

Because it's stateless and short-lived, you generally can't revoke it directly before it expires — this is exactly why it should be short-lived (minutes, not days). Mitigations:

  • Maintain a small denylist in Redis (token ID / jti claim) for emergency revocation of specific tokens before natural expiry.
  • Revoke the associated refresh token immediately so no new access tokens can be minted once the leaked one expires.
  • Force re-authentication for the affected user, and audit logs for suspicious activity during the exposure window.

Unlike access tokens, refresh tokens are stored server-side, so you can act directly:

  • Revoke it immediately — delete/invalidate it in the DB/Redis store.
  • Implement refresh token rotation: every time a refresh token is used, issue a brand-new one and invalidate the old — if an old (already-rotated) token is ever reused, that's a strong signal of theft, and you can revoke the entire token family and force re-login.
  • Notify the user of the security event and force a password reset if warranted.

A pure stateless JWT is valid until it expires — there's no server state to "delete" on logout. Common approaches:

  1. Short access-token expiry + revocable refresh token (most common) — "logout" just deletes the refresh token server-side; the access token naturally expires within minutes.
  2. Denylist in Redis — store revoked token IDs (jti) with a TTL matching the token's remaining lifetime; check the denylist on every verification.
  3. Allowlist / session-versioning — store a tokenVersion per user; incrementing it on logout instantly invalidates all previously issued tokens for that user (checked against the claim in the JWT payload).

Role-Based Access Control — permissions are assigned to roles (admin, editor, viewer), and users are assigned roles, rather than managing permissions per-user directly.

const permissions = {
  admin:  ['users:read', 'users:write', 'orders:read', 'orders:write'],
  editor: ['orders:read', 'orders:write'],
  viewer: ['orders:read'],
};

function authorize(requiredPermission) {
  return (req, res, next) => {
    const userPerms = permissions[req.user.role] || [];
    if (!userPerms.includes(requiredPermission)) {
      return res.status(403).json({ message: 'Forbidden' });
    }
    next();
  };
}

Your own JWT-based login is authentication for your own app — you issue and verify the tokens yourself. Node.js & Express Security

Cross-Site Scripting — an attacker injects malicious <script> content that runs in other users' browsers, typically via unescaped user input rendered back into HTML (e.g. a comment field).

  • Never render raw user input as HTML — escape it, or use a templating engine that auto-escapes by default (EJS's <%= %> escapes; <%- %> does not).
  • Set a strict Content-Security-Policy header (via helmet) restricting where scripts can load from.
  • Sanitize any HTML you must accept from users with a library like DOMPurify/sanitize-html.

Cross-Site Request Forgery — a malicious site tricks a logged-in user's browser into sending an unwanted request to your app (browsers auto-attach cookies to same-origin requests, so a forged request looks "authenticated").

  • Use SameSite=Strict/Lax cookies — stops the browser from sending them on cross-site requests in the first place.
  • CSRF tokens — a random token embedded in forms/headers that the server verifies matches what it issued (via csurf or a modern equivalent).
  • Note: pure token-based (JWT in an Authorization header, not a cookie) APIs are largely immune, since there's no cookie for the browser to auto-attach.

Instead of injecting SQL syntax, an attacker injects a query operator (e.g. in MongoDB) via JSON input to bypass logic.

// Attacker sends this as the "password" field instead of a string:
{ "email": "admin@x.com", "password": { "$gt": "" } }
// If not sanitized, MongoDB interprets $gt as "greater than empty string" — always true, login bypassed

Prevention: validate/whitelist the type and shape of input (reject objects where a string is expected) using a schema validator (Joi/express-validator), and libraries like express-mongo-sanitize to strip $/. keys from user input before it reaches a query.

  • Validate file type by actual content (magic bytes / file-type library), not just the trusted-looking Content-Type header or file extension, which are trivially spoofed.
  • Limit file size (e.g. Multer's limits: { fileSize }) to prevent disk-filling/DoS.
  • Never execute or serve uploads from the same origin/permissions as your app — store in object storage (S3) or a directory with no execute permission, ideally behind a separate domain/CDN.
  • Rename files on save (don't trust the original filename — path traversal / overwrite risk) and strip/regenerate metadata for images.
  • Scan uploads with an antivirus/malware scanner where feasible for sensitive systems.

An attacker manipulates a file path input (e.g. ../../etc/passwd) to escape the intended directory and access arbitrary files on the server.

// VULNERABLE
app.get('/files/:name', (req, res) => {
  res.sendFile(`/uploads/${req.params.name}`); // name = "../../.env" â†’ leaks secrets!
});

// SAFE — resolve and verify the path stays within the intended directory
const path = require('path');
const safePath = path.join('/uploads', path.basename(req.params.name));

Happens when your server makes an outbound request to a URL supplied by the user without restriction — an attacker can point it at internal-only services (e.g. cloud metadata endpoints, internal admin panels) that aren't reachable from the public internet, using your server as a proxy.

Prevention: whitelist allowed domains/protocols for any "fetch this URL" feature, block requests to private IP ranges (169.254.x.x, 10.x.x.x, 127.0.0.1, etc.), and never let user input directly construct a server-side request without validation.

Insecure Direct Object Reference — the API trusts a client-supplied ID and fetches the resource without checking the requester actually owns/can access it.

// VULNERABLE — any logged-in user can view ANY invoice by guessing IDs
app.get('/invoices/:id', authenticate, async (req, res) => {
  const invoice = await Invoice.findByPk(req.params.id);
  res.json(invoice);
});

// FIXED — scope the query to the authenticated user
app.get('/invoices/:id', authenticate, async (req, res) => {
  const invoice = await Invoice.findOne({ where: { id: req.params.id, userId: req.user.id } });
  if (!invoice) return res.status(404).json({ message: 'Not found' });
  res.json(invoice);
});

This is one of the most commonly found bugs in real security audits — always add an ownership/permission check, don't rely on the ID being "hard to guess".

  • Rate limit login attempts per IP and per account (e.g. 5 attempts / 15 min).
  • Progressive delays / account lockout after repeated failures (with care to avoid a denial-of-service where an attacker locks out a legitimate user).
  • CAPTCHA after a few failed attempts.
  • Always return a generic error message ("Invalid email or password") — never reveal whether the email exists, which would let attackers enumerate valid accounts.

Dedicated secrets managers — AWS Secrets Manager, HashiCorp Vault, Kubernetes Secrets (backed by a KMS) — provide encryption at rest, fine-grained access control, audit logging of who accessed what, and easy rotation without redeploying code. Prefer these over plain environment variables for production-grade sensitive credentials.

  • Run npm audit (or Snyk/Dependabot) regularly and in CI, blocking on critical/high findings.
  • Keep dependencies reasonably up to date — enable automated dependency-update PRs (Dependabot/Renovate).
  • Pin exact versions in package-lock.json so builds are reproducible and a compromised upstream package version can't silently slip in.
  • Minimize dependency count — every added package is added attack surface (supply-chain risk).

Logging & Monitoring

console.log is synchronous, unstructured (plain text), has no log levels, and can't be routed anywhere but stdout. A proper logger (Winston or Pino, which is significantly faster) gives you:

  • Log levels — error/warn/info/debug, filterable per environment.
  • Structured (JSON) output — machine-parseable by log aggregators.
  • Transports — write to files, a log-aggregation service, etc., simultaneously.
const pino = require('pino')();
pino.info({ userId: 42, action: 'login' }, 'User logged in');
// {"level":30,"time":..., "userId":42, "action":"login", "msg":"User logged in"}

A unique ID generated when a request enters the system, attached to every log line produced while handling it (and forwarded to any downstream service calls it makes). Without it, in a system handling hundreds of concurrent requests, log lines from different users' requests are hopelessly interleaved — you can't tell which log lines belong to the failing request a user is reporting.

With it, you filter your log aggregator by requestId=abc123 and see the exact path that one request took, across every service it touched.

Logging as structured data (JSON) with consistent fields (timestamp, level, service, requestId, message, and relevant context), instead of free-form text strings. This lets log aggregators (ELK, Datadog, CloudWatch) query and filter logs like a database — e.g. "show all error-level logs from the payments service for user 42 in the last hour" — impossible to do reliably against unstructured text.

A lightweight endpoint (e.g. GET /health) that reports whether the service (and its critical dependencies — DB, Redis) is up and able to serve traffic. Load balancers, Kubernetes probes, and uptime monitors poll it to decide whether to route traffic to an instance or restart/replace it.

app.get('/health', async (req, res) => {
  const dbOk = await checkDbConnection();
  const redisOk = await checkRedisConnection();
  const healthy = dbOk && redisOk;
  res.status(healthy ? 200 : 503).json({ db: dbOk, redis: redisOk });
});

Application Performance Monitoring — automatically instruments your app to track request latency, throughput, error rates, and traces individual requests across services (distributed tracing), usually with minimal code changes via an agent.

Tools: New Relic, Datadog APM, Dynatrace, Elastic APM, open-source OpenTelemetry (vendor-neutral instrumentation standard).

  1. Get the approximate time and, if possible, a request/correlation ID (from an error toast, a support ticket, or by asking the user to reproduce it while you watch logs live).
  2. Search the centralized log aggregator (ELK/Datadog) for that request ID or the user's ID around that timestamp.
  3. Follow the trail: Load Balancer → App → Middleware → DB/Cache/External API — the structured logs at each hop show exactly where it failed and with what error.
  4. Cross-check APM traces for that time window for latency spikes or error-rate anomalies even if logs are sparse.
  5. Reproduce locally/in staging with the same input once the failing component is identified, then fix and add a regression test.

Supertest makes real HTTP-style requests against your Express app object without needing to actually bind a port.

const request = require('supertest');
const app = require('../app');

describe('GET /users/:id', () => {
  it('returns 200 and the user for a valid id', async () => {
    const res = await request(app).get('/users/1');
    expect(res.status).toBe(200);
    expect(res.body).toHaveProperty('id', 1);
  });

  it('returns 404 for a non-existent user', async () => {
    const res = await request(app).get('/users/99999');
    expect(res.status).toBe(404);
  });
});

Tests should never depend on a real third-party service (slow, flaky, costs money, no control over its response). Mock the module that makes the call.

jest.mock('../services/paymentGateway');
const paymentGateway = require('../services/paymentGateway');

it('marks order as paid when payment succeeds', async () => {
  paymentGateway.charge.mockResolvedValue({ success: true, id: 'ch_123' });

  const result = await processOrder(order);

  expect(result.status).toBe('paid');
  expect(paymentGateway.charge).toHaveBeenCalledWith(order.amount);
});

For HTTP-level mocking specifically, libraries like nock intercept outgoing requests without touching your code's structure at all.

  • Use a separate test database (never run tests against production or shared dev data).
  • Reset state between tests — wrap each test in a transaction and roll it back afterward (fast), or truncate relevant tables in a beforeEach.
  • Seed only the minimal fixture data each test actually needs, created explicitly in the test itself rather than relying on a shared global seed — keeps tests independent and easy to reason about.

Coverage measures what percentage of your code is executed by the test suite (line/branch/function coverage), typically reported by Jest's built-in coverage tool.

100% is usually not a meaningful goal — it's easy to hit 100% with shallow tests that execute a line without actually asserting meaningful behavior, and some code (trivial getters, generated boilerplate) isn't worth testing. Better to target high coverage on business-critical logic and treat the overall number as a signal, not the goal itself.

  1. Write a test that reproduces the exact failing scenario (the specific input/state that triggered the bug) — confirm it fails against the old (buggy) code first.
  2. Apply the fix; confirm the same test now passes.
  3. Commit the test alongside the fix — this guarantees the same bug can't silently reappear in a future refactor.

Production Scenarios — Node.js & Express Layer

  1. Take a CPU profile under load — node --prof then process it with node --prof-process, or attach Chrome DevTools' profiler via node --inspect, to get a flame graph of where time is spent.
  2. Common culprits: an accidental infinite/long loop, unbounded recursion, a regex vulnerable to ReDoS (catastrophic backtracking) on attacker-supplied input, synchronous JSON operations on huge payloads.
  3. Check if it correlates with a specific endpoint/traffic pattern (APM request breakdown) rather than being uniform across all traffic.

Symptoms: requests that should be fast (even simple health checks) suddenly take seconds; the whole app becomes unresponsive at once (a signature that distinguishes it from a slow DB query, which usually only affects requests touching that query).

Detect: measure event-loop lag directly — schedule a setImmediate/short setInterval and measure how late it actually fires vs. expected; libraries like toobusy-js or Node's built-in perf_hooks.monitorEventLoopDelay() do this. A growing lag confirms something synchronous is hogging the thread.

Fix: find and move the blocking synchronous code off the main thread (worker_threads, break into async chunks, or offload to a separate service).

  • Distinguish legitimate spike (e.g. a marketing campaign) from a credential-stuffing attack — check if it's spread across many IPs/accounts (likely an attack) vs one campaign source.
  • Rate limit per IP and per account (already discussed in Ch.30-8) to blunt an attack without blocking legitimate traffic entirely.
  • Ensure bcrypt hashing (inherently CPU-costly by design) isn't itself becoming the bottleneck — this is exactly the kind of load that benefits from horizontal scaling (more instances) since each login is independent.
  • Put a CDN/WAF (Cloudflare, AWS WAF) in front to absorb volumetric abuse before it even reaches your app.
  1. If it's a signing secret that leaked (not just one token) — this is critical: rotate the JWT signing secret immediately, which invalidates every currently-issued token and forces all users to log in again.
  2. If it's a single user's token — revoke it via your denylist/token-version mechanism (Ch.29-4) and force that user to re-authenticate.
  3. Audit access logs for the exposure window for any suspicious use of the leaked token/secret.
  4. Add secret-scanning (gitleaks / GitHub secret scanning) to CI to catch this before merge in the future.
  • Client-side: disable the submit button immediately on click (UX-level, not a real guarantee).
  • Server-side (the real fix): use the idempotency key pattern (Ch.23-8) — the client generates a unique key per logical action; the server checks/stores it (Redis) and returns the original result for a repeat.
  • For form-like resource creation without an explicit key, a short-lived debounce lock per user+action in Redis (SET key val NX EX 5) rejects a second identical request within a few seconds.
  • Never buffer the whole upload into memory — use streaming upload handling (Multer's disk storage, or stream directly to S3 via multipart upload) so memory usage stays flat regardless of file size.
  • Set sane request size limits appropriate to your use case (reject clearly-wrong sizes early via a Content-Length check before even accepting the body).
  • For very large files, prefer direct-to-storage uploads (client uploads straight to a pre-signed S3 URL) so the request never even passes through your Node app.
  • Paginate — never return unbounded result sets (Ch.28-2); this is the primary fix in almost every real case.
  • If a genuine bulk export is needed, stream the response (e.g. stream rows out as newline-delimited JSON or CSV) instead of building the entire array in memory and calling res.json() once at the end.
  • For heavy exports, consider generating the file asynchronously (background job) and notifying/emailing the user a download link when ready, rather than holding an HTTP connection open for minutes.
  • Recovery: run under a process manager (PM2) or orchestrator (Kubernetes) that auto-restarts a crashed process immediately — this should already be in place before the crash happens, not set up after.
  • Diagnose: check the crash logs for the actual error — most crashes are an uncaught exception or unhandled promise rejection that Node treats as fatal.
  • Prevent recurrence: ensure every route has proper error handling (Ch.17-1/17-2), add global process.on('uncaughtException')/('unhandledRejection') handlers that log and gracefully shut down rather than crashing silently/inconsistently, and run multiple instances so one crash doesn't cause a full outage.
  • On Kubernetes: kubectl rollout undo deployment/<name> — reverts to the previous ReplicaSet's image, itself performed as a safe rolling update.
  • Without K8s: keep the previous Docker image tagged/available and redeploy it the same way (PM2 reload / re-run the previous container).
  • The hard part is usually the database — if the failed deploy included a migration, make sure migrations are backward-compatible (Ch.23-10) so the rolled-back old code still works against the new schema; a bad migration may need its own explicit down-migration, not just a code rollback.
  • Prevention: canary/staged rollouts (deploy to a small % of traffic first) catch this before it affects everyone.
