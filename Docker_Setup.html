Shuru Karne Se Pehle — Docker Kyun Aaya?

Problem Docker se pehle (2013 se pehle)

Ek company apna app 3 jagah deploy karti thi — dev laptop, testing server, production server. Har jagah:

  1. Manually setup karna padta tha — Node install karo, sahi version, sahi OS packages, sahi environment variables. Har naye server pe ghanton lagte the.
  2. "Works on my machine" problem — dev ke laptop pe chalta tha, production pe crash ho jaata tha, kyunki dono jagah ki OS/library versions thodi alag hoti thi.
  3. Virtual Machines tab available thi (isolation ke liye), lekin VM bahut heavy thi — poora OS boot karna padta (GBs ki size, minutes ka boot time). Ek server pe 20-30 se zyada VMs nahi chala sakte the — resources khatam ho jaate.

Turning point — Microservices ka trend

Companies badi monolithic apps ko chhote-chhote services mein todne lagi (microservices). Ab problem aur badh gayi: 15 alag services hain, aur har ek ko apni VM chahiye → 15 heavy VMs = bahut zyada cost + resources. Har service ki apni dependency versions ho sakti hain, inko isolate karna zaroori tha, lekin VM jaisa heavyweight isolation nahi chahiye tha.

Docker ne kya solve kiya

2013 mein Docker aaya, jisne bola: "Poora OS boot karne ki zaroorat nahi — Linux kernel mein pehle se namespaces/cgroups features hain jo lightweight isolation de sakte hain."

Problem (before)Docker ka solution
"Works on my machine"App + dependencies ek image mein pack — jahan chalao, same environment
VM heavy hai (GBs, minutes)Container light hai (MBs, seconds) — kernel share karta hai
Manual server setup ghanton leta haidocker run se seconds mein environment ready
Microservices ko 100s VMs chahiyeSame host pe 100s containers chal sakte hain (lightweight)

Ek line mein: Docker isliye banaya gaya taaki VM jaisa isolation mile, lekin VM jaisa heavy overhead na ho — aur saath mein "environment consistency" (dev=prod) ka permanent solution mil jaaye. Yeh microservices era ki zaroorat thi — bina Docker jaisi cheez ke, microservices architecture practically scale hi nahi kar sakta tha.

Poora course isi ek core problem (consistency + lightweight isolation) ko step-by-step deeper solve karne ki journey hai — pehle single container isolate karna sikhte hain (01–03), phir data persist karna (04—Volumes), phir multiple containers ko baat karwana (05—Networking), phir sab ko ek saath manage karna (06—Compose), phir secure/production-ready banana (07–08), aur aakhir mein bade scale pe orchestrate karna (09).

01

Docker Fundamentals (Internals)

Poora Concept Ek Saath — Real Project Story (TeamShop App)

Ek startup "TeamShop" apna e-commerce app bana rahi hai (Node.js + MongoDB). Dekho ek real project mein yeh saare Phase 1 concepts ek dusre se juda hokar kaise kaam karte hain:

1. What is Docker: Team ke 4 developers ke laptop pe alag-alag Node versions hain — "works on my machine" bug baar-baar aata hai. Team decide karti hai Docker use karenge, taaki app + dependencies ek portable package mein pack ho jaayein, aur jahan bhi chalao, same environment mile.

2. Containers: App ko 3 hisso mein todte hain — Auth service, Product service, Payment service — har ek apne alag container mein chalta hai. Product service crash ho jaaye (bug ki wajah se), toh Payment aur Auth bilkul unaffected rehte hain, alag-alag isolated hone ki wajah se.

3. Containers vs VMs: Pehle team VM use karne ka soch rahi thi (3 services ke liye 3 VMs) — lekin VM heavy hai (GBs, minutes ka boot). Container light hai (MBs, seconds), aur host ka kernel share karta hai — isliye same server pe teeno containers bina extra cost ke chal jaate hain.

4. Docker Architecture: Jab developer docker run chalata hai, uske peeche Client → Daemon → containerd → runc → Kernel chain kaam karti hai — command lekar, container banake, kernel-level isolation deke.

5. Docker Engine: Har developer ke laptop aur production server, dono pe Docker Engine installed hai — yehi (Daemon + API + CLI) poora system hai jo upar wali architecture chain ko chalata hai.

6. Docker CLI: Developer terminal mein docker build, docker run type karta hai — yeh commands CLI leke Engine tak bhejta hai. Baad mein yehi commands CI/CD pipeline (Jenkins) mein automatically bhi chalte hain, bina kisi insaan ke type kiye.

7. Images: Har service ka apna Dockerfile hai, jisse ek Image banti hai (jaise Product service ke liye teamshop-product:1.0) — yeh ek read-only template hai, jisse jitne chaho utne containers spin up kar sakte ho.

8. Docker Registry: Team apni images ko seedha laptop pe nahi rakhti — ek Registry (shared warehouse) pe push karti hai, taaki CI/CD server aur production server dono wahan se pull kar saken. Company apna proprietary code safe rakhne ke liye private registry (AWS ECR) use karti hai.

9. Docker Hub: Lekin apna khud ka code likhne ke alawa, team ko ready-made cheezein bhi chahiye — jaise MongoDB, Nginx. Yeh sab Docker Hub (sabse bada public Registry) se docker pull mongo karke seedha mil jaati hain — khud se MongoDB install/build nahi karna padta.

Ek line mein: Docker (problem solver) → Containers (isolated running units) → jo VMs se halke hain → inhe Architecture (Client→Daemon→containerd→runc) banati hai → jo Docker Engine ke andar hi installed hoti hai → jisse baat CLI se karte hain → jo Images (blueprint) se containers banata hai → jo Registry mein store/share hoti hain → aur Docker Hub sabse bada public Registry hai jahan se ready-made images milti hain.

Docker ek containerization platform hai jo application ko uski saari dependencies (code, runtime, libraries, OS-level config) ke saath ek portable package (image) mein pack kar deta hai, jise phir container ki tarah kahin bhi run kar sakte ho — "mere machine pe toh chal raha tha" wali problem yahin khatam ho jaati hai.

Scenario 1 — "Works on my machine" (Docker se pehle)

Ek 4-member team ek Node.js + MongoDB project pe kaam kar rahi hai. Ek din QA ko production-jaisa bug reproduce nahi ho raha:

  1. Developer A ke laptop pe Node v18 hai, code perfectly chalta hai.
  2. Developer B ke laptop pe Node v16 hai (kabhi update hi nahi kiya) — ek naya JS syntax feature use hua hai jo v16 mein silently different behave karta hai, ek subtle bug create hota hai.
  3. QA server pe MongoDB ka alag version install hai — ek query jo dev mein chal rahi thi, QA mein error deti hai.
  4. Result: sabka "mera code toh sahi hai" — ghanton debug karne ke baad pata chalta hai problem code mein nahi, environment mismatch mein thi.

Scenario 2 — Wahi setup, Docker ke saath

Ab team ek Dockerfile likh deti hai jo exact environment define karta hai:

FROM node:18-alpine     # Node version fixed — sabke liye same
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["node", "server.js"]

Ab poori team, QA, aur production — sab isi ek hi image se container chalate hain:

docker build -t myapp:1.0 .     # image banao (ek baar)
docker run -p 3000:3000 myapp:1.0   # jahan bhi chalao, andar Node v18 hi hoga

Bug turant reproduce ho gaya, kyunki QA aur dev exact same image use kar rahe the.

4 core benefits — ek-ek example ke saath

  • Consistency — upar wala hi example: dev, QA, staging, prod — sab jagah myapp:1.0 image se container chalta hai, environment kabhi drift nahi karta.
  • Isolation — ek e-commerce server pe Node API container aur Redis container dono chal rahe hain; Node app mein memory leak ho jaaye aur wo crash ho, Redis container bilkul unaffected rehta hai (alag namespace/process, alag resource limits).
  • Portability — wahi myapp:1.0 image developer ke Mac laptop, company ke on-prem Linux server, aur AWS EC2 — teeno jagah bina kisi change ke chal jaati hai.
  • Fast startup — VM boot karne mein 1-2 minute lagte (poora OS load hota hai); Docker container container host ka hi kernel use karta hai, isliye docker run se app 1-2 second mein chalu ho jaata hai — auto-scaling/CI pipelines mein yeh farq bahut matter karta hai.
Real onboarding exampleNaya developer join karta hai — bina Node, MongoDB, ya kisi bhi tool ko manually apne laptop pe install kiye, sirf docker compose up chalata hai aur poora project (API + DB) 10 second mein chalu ho jaata hai. Docker install hone ke alawa kuch aur setup hi nahi karna padta.
Common confusion — laptop ka Node upgrade/downgrade hota hai kya?

Nahi. Container image mein node:18 likhne se developer ke laptop ka actual Node kabhi touch nahi hota — wo apni jagah waisa hi (v16) pada rehta hai. Laptop ka Node aur container ke andar ka Node do bilkul alag, independent cheezein hain, bas ek hi machine pe saath-saath reh rahi hain (jaise phone aur PlayStation ek hi ghar mein, par ek dusre se unrelated).

# Laptop pe seedha terminal mein (bina Docker ke)
node -v
# → v16.x.x    (yeh developer ka apna, jo waisa hi rahega)

# Container ke andar (jo chal raha hai) check karo
docker exec -it myapp node -v
# → v18.x.x    (image mein jo pack tha, wahi milega)

Jab bhi docker run se app start hoti hai, wo sirf container ke andar wale Node ko dekhti hai — uss waqt ke liye laptop ka Node exist hi nahi karta app ke perspective se. Isi wajah se 5 developers ke laptop pe 5 alag Node versions ho sakte hain, phir bhi sab docker run karke same Node v18 wale container pe kaam karenge.

Ek Container ek image ka running, isolated instance hai — jaise ek recipe book (Image) follow karke abhi banaya/chal raha khana. Andar app chal rahi hai, apni memory, apna process, apna network le ke, lekin host machine ke kernel ko share karte hue.

Real production exampleEk e-commerce app mein 3 alag microservices hain — Auth, Payment, Product Catalog. Har ek apne alag container mein chalta hai. Agar Product Catalog container mein memory leak ho aur wo crash ho jaaye, Payment aur Auth containers bilkul unaffected rehte hain — alag "kamre" (namespace) hone ki wajah se ek ki problem dusre tak nahi pahunchti.
Yaad rakhne ka tareeka: Image = "recipe book" (fixed), Container = "abhi chal raha khana/kamra" (running, isolated, delete ho sakta hai bina recipe ko touch kiye).

Kissa — Independent Flat vs PG (Hostel) ka kamra

Socho do tarah ke rehne ke options hain:

  • Independent Flat — apna khud ka paani ka tank, apna generator, apna sab kuch alag se lagana padta hai. Bahut secure aur independent hai, lekin banane mein mahina lagta hai aur bahut mehenga hai.
  • PG (Hostel) ka ek kamra — poori building ka ek hi paani connection, ek hi bijli meter (shared) use hota hai, lekin har kamre ka apna lock hai (koi dusre ke kamre mein nahi ghus sakta), aur warden ne har kamre ki bijli/paani ki limit bhi tay kar rakhi hai. Kamra turant milta hai, bahut sasta hai.

VM = Independent Flat — apna poora guest OS chalata hai (hypervisor ke upar), apna alag kernel — heavy (GBs), slow boot (minutes). Container = PG ka kamra — host OS ka hi kernel share karta hai (ek hi building), sirf apne "kamre" (process) tak limited — light (MBs), fast boot (seconds).

Isolation kaise milta hai (interview-level detail):

  • Namespaces (= kamre ka lock) — har container ko apna isolated view milta hai: PID namespace (apne hi processes dikhte hain), Network namespace (apna IP/ports), Mount namespace (apna filesystem view), UTS (hostname).
  • cgroups (= warden ki bijli/paani limit) — container kitna CPU/memory/disk I/O use kar sakta hai, uski limit lagate hain — ek container poore host ke resources hog nahi kar sakta.

Interview trap: "Docker container ek chhota VM hai?" — Nahi. Container VM nahi hai, yeh host OS ka hi ek isolated process hai. Isi wajah se container Linux-native hai (Windows/Mac pe Docker Desktop andar ek lightweight Linux VM chalata hai).

Kabhi na bhoolne wali theory: VM = apna alag ghar (apna poora kernel/OS) — heavy, independent. Container = ek building ke andar apna kamra (shared kernel, apna lock + apni limit) — light, fast. Dono mein isolation hai, lekin VM "sab kuch apna" banata hai, Container sirf "apni jagah" banata hai.

Architecture ko neeche se upar banate hain — har layer apne se ek neeche wali layer ko "use" karti hai, khud dobara wahi kaam nahi karti.

Layer 0 — Linux Kernel (foundation)

Docker khud koi magic nahi karta — Linux kernel mein pehle se 2 features hote hain, Docker sirf unko use karta hai:

  • Namespaces — ek process ko "apni ek chhoti duniya" dikha dete hain (apna PID list, apna network, apna filesystem view). Isi se container ko lagta hai "mai akela hi chal raha hoon", jabki wahi machine pe 10 aur containers bhi chal rahe hain.
  • cgroups — kitna CPU/RAM ek process use kar sakta hai, uski limit lagate hain.

Kyun zaroori: Bina inke, "container" ka concept hi exist nahi karta — yehi do cheezein isolation create karti hain.

Layer 1 — runc (kernel ke bilkul upar)

Namespaces/cgroups ko manually set karna mushkil/error-prone hai. runc ek chhota tool hai jo instruction leta hai ("itna CPU do, yeh isolation do") aur kernel se baat karke asli container process bana deta hai (OCI standard).

Kyun zaroori: Har baar manually namespaces/cgroups set na karna pade — ek standard, reusable tool.

Layer 2 — containerd (runc ke upar)

Container banana kaafi nahi — manage bhi karna hai: start karo, stop karo, status check karo, multiple containers track karo. containerd yeh sab karta hai, aur zaroorat padne par runc ko bolta hai "ek naya container bana do".

Kyun zaroori: runc sirf "banata" hai; "kaun sa container chal raha hai, kiska status kya hai" — yeh tracking/management alag layer honi chahiye.

Layer 3 — Docker Daemon / dockerd (containerd ke upar)

Sirf container manage karna kaafi nahi — image banana (docker build), network banana, volume banana, registry se image download karna bhi chahiye. dockerd yeh sab handle karta hai, aur container-specific kaam ke liye niche containerd ko call karta hai.

Kyun zaroori: containerd sirf "container chalane" tak limited hai — image build/networking/volumes Docker ke apne extra features hain, isliye alag layer.

Layer 4 — Docker Client / CLI (sabse upar, tumhare paas)

Tum terminal mein jo type karte ho (docker run, docker build) — yeh Client hai. Yeh khud kuch nahi karta, bas command leke dockerd ko bhej deta hai (ek request ki tarah, chahe wahi machine ho).

Kyun zaroori: Isi wajah se Docker Desktop (GUI) aur terminal (CLI) dono ek hi dockerd se baat kar sakte hain — interface alag, kaam karne wala same.

Registry — side mein ek alag cheez

Yeh upar wali chain ka part nahi hai, balki ek storage jagah hai jahan images pehle se bani-banayi rakhi hoti hain (Docker Hub/ECR). Jab dockerd ko koi image local mein nahi milti, wahan se download karta hai.

Kissa — Car ka Engine

Socho ek car hai. Car chalane ke liye chahiye: engine (jo asli kaam karta hai — petrol jalana, wheels ghumana), steering wheel (jisse tum control karte ho), aur wiring/dashboard (jo steering ko engine se jodta hai).

Docker Engine = poori car ka mechanical system — ismein 3 cheezein hoti hain:

  • dockerd (Daemon) = engine khud, jo asli kaam karta hai (images/containers manage).
  • REST API = wiring, jo commands ko engine tak pahunchata hai.
  • CLI = steering wheel, jisse tum drive karte ho.
Real production exampleJab company kehti hai "humne apne server pe Docker Engine install kiya", matlab wahan poora system chal raha hai — sirf CLI nahi, balki daemon + API dono, jo background mein images/containers manage karte hain, chahe koi terminal mein command daale ya na daale.
Yaad rakhne ka tareeka: Docker Engine = "poori gaadi", Daemon = "engine", CLI = "steering wheel". Steering ke bina bhi (API se) gaadi chala sakte ho — isiliye Jenkins/Docker Desktop CLI use kiye bina bhi seedha API se Engine ko control karte hain.

Kissa — Waiter ko order dena

Restaurant mein tum waiter ko verbally order dete ho ("ek pizza"). CLI aisa hi hai — tumhare typed commands ko leke Daemon tak pahunchata hai. Yeh khud kuch nahi karta, bas message carry karta hai.

docker --version      # installed version
docker images         # local saari images list
docker ps             # running containers
docker ps -a          # sab containers (stopped bhi)
docker info           # daemon/system details
docker system df      # disk usage (images/containers/volumes)
Real production exampleCLI sirf developer ke terminal mein nahi chalta — CI/CD scripts (Jenkins, GitHub Actions) ke andar bhi wahi CLI commands (docker build, docker push) automatically chalte hain, bina kisi insaan ke type kiye.
Yaad rakhne ka tareeka: CLI = "order dene ka tareeka" — chahe insaan boley (terminal) ya machine boley (script), waiter (Daemon) tak baat wahi pahunchti hai. Aur: images = "kitni recipe books hain", ps = "abhi kitna khana ban raha hai", ps -a = "sab khana + jo khatam ho chuka wo bhi".

Kissa — Recipe Book vs Asli Khana

Socho tumhari maa ek recipe book likhti hai — usme likha hai "2 cup chawal, 1 spoon ghee, 20 min pakao." Yeh recipe book khud khana nahi hai — yeh sirf ek instruction set hai. Jab maa usse follow karke khana banati hai, tabhi asli khana (Container) taiyar hota hai, jise kha sakte ho.

Image = Recipe book — ek fixed, likha hua template (code + dependencies + config). Isme badlaav nahi hota (read-only).

Sabse important baat: Ek hi recipe book se maa kai baar khana bana sakti hai — aaj bhi, kal bhi, party mein 10 logo ke liye bhi. Ek Image se multiple Containers ban sakte hain, bilkul isi tarah.

Layers — "Recipe steps stack hote hain"

Recipe mein steps hote hain (chawal dho lo → pani daalo → namak daalo → pakao). Docker image bhi aise hi layers mein bani hoti hai — Dockerfile ki har line ek layer:

Image Layers (Union Filesystem) 
Container writable layer   ← runtime changes (logs, temp files) — sirf isi mein write
─────────────────────────
Layer 4: COPY . .            ┐
Layer 3: RUN npm install     │  Image ke read-only layers
Layer 2: WORKDIR /app        │  (Dockerfile ki har line ~ ek layer)
Layer 1: FROM node:18-alpine ┘

Docker union filesystem (OverlayFS) use karta hai — sab read-only image layers ek stack ki tarah upar-neeche merge hoke ek single filesystem view dete hain, aur container start hote hi upar ek thin writable layer add hoti hai.

  • Layers reusable/shared hote hain — 5 alag projects agar same node:18-alpine base use karte hain, toh wo base layer disk pe sirf ek baar store hoti hai, sab share karte hain. (Jaise 5 alag recipes agar "chawal dho lo" common step hai, toh wahi step hai, alag-alag nahi.)
  • Container delete hona = khana khatam hone pe plate khali ho jaana — recipe book (image) waisi ki waisi rehti hai, chaho toh phir se naya khana (naya container) bana sakte ho.
Kabhi na bhoolne wali theory: Image = read-only blueprint (layers ka stack). Container = us blueprint ka running instance (upar ek writable layer ke saath). Ek Image → Multiple Containers. Container delete = sirf writable layer gayab, Image untouched rehti hai.
Trick: "Image = Recipe (fixed), Container = Khana jo plate mein bana (temporary, dobara bana sakte ho)."

Kissa — Godaam (Warehouse)

Socho ek bada godaam hai jahan bani-banayi cheezein (images) rakhi hoti hain — koi bhi wahan se apni zaroorat ki cheez uthake (pull) le sakta hai, ya apni banayi cheez wahan rakh (push) sakta hai.

Registry ek general term hai — koi bhi jagah jo Docker images store karti hai. Do tarah ki ho sakti hai:

  • Public Registry — sabke liye khula godaam (Docker Hub).
  • Private Registry — company ka apna locked godaam (AWS ECR, GitLab Container Registry, Harbor) — sirf company ke log access kar sakte hain.
Real production exampleCompany apna proprietary/secret code kabhi Docker Hub (public) pe push nahi karti — wahan private registry (jaise AWS ECR) use karte hain, taaki source code leak na ho, sirf company ke servers hi wahan se pull kar sakein.
Yaad rakhne ka tareeka: Registry = "godaam ka general naam" (kaisa bhi ho, public ya private) — jaise "dukaan" ek general word hai, chahe Kirana store ho ya Big Bazaar.

Kissa — Sabse Bada Public Godaam

Docker Hub = Registry ka sabse bada, sabse popular public version (jaise Amazon — sabse bada public marketplace). Yeh Docker company ka apna official Registry hai.

docker pull node:18-alpine    # Docker Hub se hi aa raha hai (default)
docker pull mongo
docker pull nginx
Real production exampleJab bhi tum docker pull node likhte ho (bina kisi aur registry ka naam diye), Docker by default Docker Hub se hi download karta hai. Real projects mein "official images" (Node, MongoDB, Nginx, Redis — jo khud company banati/verify karti hai) yahin se milti hain; apna khud ka open-source project image bhi yahan free mein publish kar sakte ho.
Yaad rakhne ka tareeka: Docker Hub = "sabse bada public Registry". Har Docker Hub ek Registry hai, lekin har Registry Docker Hub nahi hai (jaise "har Xerox photocopier hai, har photocopier Xerox nahi").
Quick Revision — Fundamentals Summary
  • Docker — app + dependencies ko portable container mein pack karta hai; "works on my machine" problem solve karta hai.
  • Container — ek image ka running, isolated instance; ek crash ho toh dusre unaffected rehte hain.
  • vs VM — container host kernel share karta hai (namespaces + cgroups), VM apna poora guest OS chalata hai; container light aur fast hai.
  • Architecture — CLI → dockerd → containerd → runc → kernel; images Registry (Docker Hub/ECR) se aati hain.
  • Docker Engine — dockerd + REST API + CLI ka combined system.
  • Docker CLI — commands leke Daemon tak pahunchata hai; terminal aur CI/CD scripts dono use karte hain.
  • Image — read-only blueprint (layers ka stack); Container uska running instance; layer sharing se disk space bachta hai.
  • Registry — general term, images store karne ki jagah (public ya private).
  • Docker Hub — sabse bada public Registry, official images (Node/Mongo/Nginx) ka default source.

Dockerfile & Image Optimization

FROM node:18-alpine        # base image
WORKDIR /app                # container ke andar working directory
COPY package*.json ./       # pehle sirf dependency files copy
RUN npm install             # dependencies install (build-time)

Docker har instruction ko ek layer banata hai aur cache karta hai. Rebuild pe, jis line tak kuch change nahi hua, uske upar ki saari layers cache se reuse hoti hain — jahan se change shuru hua, wahan se neeche saari layers dobara banti hain.

Bad Order (slow rebuilds)Good Order (fast rebuilds)
COPY . .
RUN npm install
COPY package*.json ./
RUN npm install
COPY . .

Real problem, step-by-step: "Bad order" mein agar sirf ek .js file change hui (dependencies same hain), tab bhi COPY . . ki wajah se cache invalidate ho jaata hai, aur uske baad wala npm install dobara puri run hota hai — unnecessarily 2-3 minute waste. "Good order" mein package.json change na ho toh npm install wali layer cache se hi mil jaati hai, sirf last COPY . . dobara chalta hai — build seconds mein.

Rule of thumb: Jo cheez kam badalti hai (dependencies) usko upar rakho, jo zyada badalti hai (source code) usko neeche.

Problem: React app build karne ke liye poora Node.js + node_modules + build tools chahiye (~1GB+), lekin production mein sirf static HTML/CSS/JS files serve karni hoti hain — agar single-stage Dockerfile banao, final image mein saara build junk bhi reh jaata hai, image unnecessarily bahut badi ban jaati hai.

Solution — Multi-stage build: Ek se zyada FROM stages use karo — pehle stage mein build karo, doosre (final) stage mein sirf build ka output copy karo, poora build environment discard ho jaata hai.

# Stage 1 — build
FROM node:18 AS build
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build              # dist/ folder banta hai

# Stage 2 — production (sirf output copy)
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Result: Final image mein Node.js, node_modules, source code — kuch bhi nahi, sirf compiled static files + Nginx. Image size 1GB+ se ghatke ~25-40MB tak aa sakta hai.

Real project mein use: Har production-grade React/Angular/Vue Docker setup mein multi-stage build standard practice hai; Node.js API ke liye bhi devDependencies/TypeScript compile step ko alag stage mein karke sirf compiled JS final image mein rakhte hain.

  • Alpine/distroless base images — node:18 (~1GB) ke bajaye node:18-alpine (~180MB) ya distroless (bina shell/package-manager ke, sirf runtime) use karo.
  • Multi-stage builds (upar dekha) — build tools final image mein na rakhna.
  • .dockerignore — node_modules, .git, .env, logs jaisi files build context mein bhejne se rokta hai:
node_modules
.git
.env
*.log
Dockerfile
.dockerignore

Without .dockerignore: Local node_modules poore build context ke saath daemon ko bheja jaata hai (slow build) aur agar COPY . . hai toh wahi purana/wrong-platform node_modules image mein chala jaata hai, jo RUN npm install ke fresh install ko override kar sakta hai — bugs.

  • Combine RUN commands — har RUN ek layer banata hai; related commands ko && se combine karke layers kam karo aur apt cache clean karo (rm -rf /var/lib/apt/lists/*).

    • BuildKit Docker ka naya, faster build engine hai (ab default) — parallel layer builds, better caching, aur secrets/SSH mount support deta hai jo purana builder nahi deta tha.

    # Secret ko image layer mein bake hue bina use karna (BuildKit feature)
RUN --mount=type=secret,id=npm_token \
    npm config set //registry.npmjs.org/:_authToken=$(cat /run/secrets/npm_token) \
    && npm install

    docker buildx BuildKit ka CLI plugin hai jo multi-architecture images (jaise amd64 + arm64 ek saath) build karne deta hai:

    docker buildx build --platform linux/amd64,linux/arm64 -t myapp:latest --push .

    Real project mein use: Team ke kuch developers Mac M1 (ARM) pe hain, production servers Intel (AMD64) pe — ek hi buildx command se dono architecture ke liye image ban jaati hai, "exec format error" jaisi runtime mismatch errors nahi aatin.

    docker build -t myusername/myapp:1.0 .
docker login
docker push myusername/myapp:1.0
docker pull myusername/myapp:1.0

    Real project mein use: CI/CD pipeline build ke baad image ko tag karke registry pe push karta hai, production server wahan se pull karke naya container start karta hai — source code seedha production pe copy nahi hota, sab image ke through jaata hai.

    Quick Revision — Dockerfile Summary
    • Instructions — FROM/WORKDIR/COPY/RUN/ENV/ARG/EXPOSE/CMD; ARG build-time only, ENV runtime tak persist.
    • CMD vs ENTRYPOINT — CMD replace hota hai, ENTRYPOINT ke args append hote hain; dono combine karna common senior pattern hai.
    • COPY vs ADD — COPY predictable/plain; ADD tar-extract/URL-download karta hai, isliye avoid karte hain.
    • Layer caching — kam-badalne-wali cheezein (dependencies) upar, zyada-badalne-wali (source code) neeche rakho.
    • Multi-stage builds — build stage alag, final stage mein sirf output — image size drastically kam.
    • Size reduction — Alpine/distroless base, .dockerignore, combined RUN commands.
    • BuildKit/buildx — faster builds, secret mounts, multi-architecture (amd64+arm64) images.

    exec vs attach: exec ek naya process container ke andar start karta hai (jaise debug shell) — exit karne pe container chalta rehta hai. attach container ke main process (PID 1) se seedha judta hai — galti se Ctrl+C daba diya toh main process hi ruk sakta hai, container stop ho jaayega. Isi wajah se debugging ke liye exec zyada safe hai.

    #docker stopdocker kill
    SignalSIGTERM bhejta hai, phir grace period (default 10s) wait karta haiSIGKILL seedha bhejta hai — turant
    Graceful?Haan — app ko cleanup ka time milta hai (open DB connections close, in-flight requests finish)Nahi — process turant force-terminate
    Timeout par kyaAgar 10s mein app khud exit nahi hui, Docker khud SIGKILL bhej deta haiN/A

    Real project mein use: Deploy/restart ke waqt hamesha docker stop use karte hain (ya orchestrator khud yehi karta hai) — app ko SIGTERM handle karke graceful shutdown ka mauka milta hai (jaise ongoing HTTP requests complete karna, DB connection close karna). kill sirf tab jab process hang/unresponsive ho aur graceful stop kaam na kare.

    Container ke andar jo bhi process CMD/ENTRYPOINT se start hota hai, wo PID 1 ban jaata hai. Normal Linux system mein PID 1 (init/systemd) ke special jobs hote hain jo container ke andar Node/Python jaisi apps khud nahi karti:

    • Signal handling — kernel default signal behavior sirf PID 1 ke liye alag hota hai; agar app khud explicitly SIGTERM handler register nahi karti, container graceful shutdown ke bajaye seedha kill ho sakta hai poore 10s wait ke baad.
    • Zombie process reaping — agar app andar se child processes spawn karti hai (jaise shell scripts), aur wo child exit ho jaaye, unka exit-status kisi ko "reap" karna padta hai. Normal init yeh khud karta hai; PID 1 pe chal rahi simple app (jaise Node) yeh nahi karti — zombie processes accumulate hote rehte hain.
    Fix — Init process use karo 
    docker run --init myimage
# ya Dockerfile mein
ENTRYPOINT ["/tini", "--", "node", "server.js"]

    Real project mein use: docker run --init flag (ya tini jaisa lightweight init tool) daalte hain — yeh ek chhota init process PID 1 pe baithata hai, jo signals sahi se forward karta hai aur zombie processes reap karta hai, asli app ko clean environment milta hai.

    Real scenario — OOM Kill

    1. Container ko --memory=512m di gayi hai.
    2. App mein memory leak hai — usage dheere-dheere badhta hai.

    4. docker inspect mein "OOMKilled": true dikhta hai — yeh confirm karta hai crash memory-limit ki wajah se hua, kisi normal bug se nahi.

    Real project mein use: Production mein hamesha memory/CPU limits set karte hain, taaki ek faulty service poore host/cluster ko down na kar de; Kubernetes mein isi concept ko resources.limits kehte hain.

    Scenario: Production mein ek container docker ps mein baar-baar "Restarting" dikha raha hai. Step-by-step troubleshooting:

    Quick Revision — Containers & Debugging Summary
    • Lifecycle — run/start/stop/rm/exec/logs; exec naya process spawn karta hai, attach risky hai (main process se juda).
    • stop vs kill — stop = SIGTERM + grace period (graceful); kill = SIGKILL turant (force).
    • PID 1 problem — app khud signal handle/zombie reap nahi karti — --init ya tini use karo.
    • Diagnostics — inspect (config/state), stats (live resources), top (andar ke processes).
    • Resource limits — --memory/--cpus na ho toh ek leak poore host ko OOM kill tak le ja sakta hai.
    • Crash debugging — exit code check karo (137=OOM), logs dekho, --entrypoint sh se interactively andar jaao.
    • Restart policy — production mein unless-stopped common choice.

    Volumes & Data Persistence

    Container ki writable layer temporary hoti hai — container delete (docker rm) hote hi uska saara data hamesha ke liye gayab ho jaata hai. Database jaisi stateful cheez ke liye yeh disaster hai — container restart/update karte hi saara data loss.

    Solution: Data ko container ki writable layer ke bajaye host filesystem (ya Docker-managed location) pe rakho, jo container life-cycle se independent ho.

    #Bind MountNamed Volumetmpfs
    LocationHost ka specific path (jo tum decide karo)Docker-managed location (/var/lib/docker/volumes/...)Host RAM (disk pe kabhi nahi jaata)
    Managed byTumhara OS/filesystemDocker khudDocker (memory)
    PersistenceYesYesNo — container/reboot pe gayab
    Use caseLocal dev — live code reloadProduction DB data, portable backupsSensitive temp data (secrets in-memory)
    # Bind mount — local dev, live code changes reflect
docker run -v $(pwd):/app myimage

# Named volume — production DB
docker run -v mongo_data:/data/db mongo

# tmpfs — sensitive temp data, RAM only
docker run --tmpfs /app/temp myimage

    Real project mein use: Local development mein bind mount se source code change karte hi container ke andar bhi reflect ho jaata hai (nodemon ke saath live reload). Production mein named volume use karte hain kyunki wo Docker CLI (docker volume) se manage/backup karna easy hota hai aur host filesystem structure pe depend nahi karta.

    Real scenario: Dockerfile mein security best-practice follow karke container ko non-root user (jaise UID 1000) se run karwaya. Local machine pe bind mount kiya:

    docker run -v $(pwd)/uploads:/app/uploads myimage

    Container ke andar UID 1000 user file likhne ki koshish karta hai, lekin host ke uploads/ folder ka owner UID 1001 hai (host machine ka apna user) — Permission denied error, bhale hi container "successfully" chal raha ho.

    Wajah: Bind mounts container ke andar host ke same UID/GID ko carry karte hain — Linux permission checking UID number se hoti hai, username se nahi; container ke andar ka user (UID 1000) aur host folder ka owner (UID 1001) match nahi karte.

    Fixes

    # 1) Host folder permission open kar do (dev-only, production mein risky)
chmod -R 777 uploads/

# 2) Container ke user ka UID host user ke UID se match karo
docker run --user $(id -u):$(id -g) -v $(pwd)/uploads:/app/uploads myimage

# 3) Dockerfile mein hi specific UID create karo jo host se match ho
RUN addgroup -g 1001 appgroup && adduser -u 1001 -G appgroup -D appuser
USER appuser

    Interview line: Yeh classic "isolation ka side-effect" hai — container process host se isolated dikhta hai, lekin bind-mounted filesystem permissions host ke UID system se hi govern hoti hain.

    # Backup — temporary container se volume ko tar mein compress karo
docker run --rm -v mongo_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/mongo_backup.tar.gz /data

# Restore — naye volume mein extract karo
docker run --rm -v mongo_data:/data -v $(pwd):/backup alpine \
  tar xzf /backup/mongo_backup.tar.gz -C /

    Real project mein use: Production DB volume ka daily automated backup CI/CD cron job se isi pattern se liya jaata hai, aur cloud storage (S3) pe upload kiya jaata hai.

    docker volume create mongo_data
docker run -d --name mongodb -v mongo_data:/data/db -p 27017:27017 mongo

    Ab container docker rm mongodb se delete bhi kar do aur wapas naya container same volume ke saath start karo, saara data wahi ka wahi milega:

    docker rm -f mongodb
docker run -d --name mongodb -v mongo_data:/data/db -p 27017:27017 mongo
# data intact — kyunki data container mein nahi, volume mein tha
    Quick Revision — Volumes Summary
    • Kyun chahiye — container writable layer temporary hai; container delete = data loss, bina volume ke.
    • Bind mount — host ka specific path, dev/live-reload ke liye.
    • Named volume — Docker-managed, production DB data ke liye.
    • tmpfs — RAM-only, sensitive temp data.
    • Permission mismatch — container UID aur host folder owner UID alag hone se "Permission denied"; fix: --user flag ya matching UID.
    • Backup — temporary alpine container se volume ko tar karke external storage mein le jaate hain.

    Networking

    DriverKaamKab use
    bridge (default)Container ko ek private internal network deta hai, host se isolated, NAT ke through bahar jaata haiSingle-host apps, most common default
    hostContainer koi alag network namespace use nahi karta — seedha host ka network use karta haiMax performance chahiye, port mapping ki zaroorat nahi (Linux-only)
    noneKoi networking hi nahiPure offline/isolated batch processing jobs

    Default bridge network (docker0) pe containers ek-dusre se sirf IP address se baat kar sakte hain (koi built-in DNS nahi) — aur IP restart pe change ho sakta hai, isliye hardcode karna fragile hai.

    Custom (user-defined) bridge network banate hi Docker ek automatic DNS resolution deta hai — container apne container/service name se ek-dusre ko ping/connect kar sakte hain, IP yaad rakhne ki zaroorat nahi.

    docker network create mynet

docker run -d --name mongodb --network mynet mongo
docker run -d --name api --network mynet -p 3000:3000 myapi
# api container ke andar code mein: mongodb://mongodb:27017/mydb
#                                            ^^^^^^^ — container naam hi hostname ban gaya

    Interview trap: "Default bridge use kyun nahi karte production mein?" — kyunki uspe DNS-based service discovery nahi milta, sirf IP se connect karna padta hai jo unreliable hai. Isliye hamesha custom network banao.

    #EXPOSE (Dockerfile)-p / --publish (docker run)
    EffectSirf documentation/metadata — "yeh container is port pe sunta hai"Actual host-to-container port binding karta hai
    Bina iskeContainer phir bhi us port pe sun sakta haiBina -p ke, container ka port host se accessible nahi hoga

    Interview gotcha: Bahut log samajhte hain EXPOSE 3000 likhne se port "khul" jaata hai — galat. Yeh sirf ek hint hai (aur docker run -P capital-P ke saath saari EXPOSEd ports ko random host ports pe map karne ke kaam aata hai). Asli binding -p host:container se hi hoti hai.

    docker network create app_network

docker run -d --name mongodb --network app_network -v mongo_data:/data/db mongo

docker run -d --name node_api --network app_network -p 3000:3000 \
  -e MONGO_URL=mongodb://mongodb:27017/myapp myapi

    Node app ke andar connection string mein mongodb (container name) hi hostname ki tarah use hota hai — Docker ka internal DNS ise resolve kar deta hai, actual IP kabhi hardcode nahi karna padta.

    Quick Revision — Networking Summary
    • Drivers — bridge (default, single host), host (no isolation), none (no network), overlay (multi-host).
    • Default vs custom bridge — custom bridge pe container-name-based DNS milta hai, default pe nahi.
    • EXPOSE vs -p — EXPOSE sirf documentation, -p asli port binding karta hai.
    • Real pattern — custom network banao, containers ko usme daalo, connection string mein container name use karo.

    Real project mein use: Local development mein poori team ek hi docker-compose.yml commit karti hai — naya developer sirf docker compose up chalaye, poora environment (API + DB + cache) uske machine pe ready ho jaata hai, bina manually har service install kiye.

  app_network:

    KeyMatlab
    buildLocal Dockerfile se image build karo (vs image: jo ready-made pull karta hai)
    portsdocker run -p ka YAML equivalent
    environmentEnv vars (ya env_file: se ek file se load)
    depends_onStartup order control karta hai (agla point mein detail)

    Common misconception: depends_on: mongodb likhne ka matlab yeh nahi hai ki API container tab tak wait karega jab tak MongoDB fully ready (accepting connections) na ho jaaye — yeh sirf itna guarantee karta hai ki MongoDB container start ho chuka hai (container process launch ho gaya), uske andar ka database engine abhi bhi initialize ho raha ho sakta hai.

    Real bug jo isse hota hai 
    t=0s   mongodb container start hua (process launched)
t=0.1s api container bhi start ho gaya (depends_on satisfied)
t=0.2s api MongoDB se connect karne ki koshish karta hai
       → "Connection refused" — MongoDB abhi initialize ho raha tha!
t=2s   MongoDB actually ready hota hai — par tab tak api crash ho chuka

    Fix — healthcheck ke saath condition

    services:
  mongodb:
    image: mongo:6
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    build: .
    depends_on:
      mongodb:
        condition: service_healthy   # ab genuinely "ready" hone tak wait karega

    Real project mein use: Ya phir app-level pe hi retry logic likhte hain (Mongoose/DB client connection retry with backoff) — production-grade apps dono approaches combine karte hain, kyunki network/infra level pe kabhi bhi temporary disconnect ho sakta hai.

    Ek hi docker-compose.yml mein dev aur prod dono ka config mix karna messy hota hai. Compose override files aur profiles se alag-alag environments manage karte hain.

# docker-compose.prod.yml — explicit prod overrides

docker compose up                                            # base + override.yml (auto)
docker compose -f docker-compose.yml -f docker-compose.prod.yml up   # base + prod explicitly

    docker compose up -d       # sab services background mein start
docker compose logs -f api  # sirf api service ke logs
docker compose down         # sab stop + network cleanup (volumes rehte hain)
docker compose down -v      # volumes bhi delete (careful — data loss)
    Quick Revision — Docker Compose Summary
    • Kyun — multi-container app ko ek YAML se, ek command se manage karta hai.
    • Structure — services, networks, volumes top-level keys; build vs image.
    • depends_on gotcha — sirf "container started" guarantee karta hai, "app ready" nahi — condition: service_healthy ya retry logic chahiye.
    • Override files — base + override.yml (dev, auto-merge) + prod.yml (explicit) — ek base, alag environments.
    • Production mein Compose sirf single-host hai — multi-host scaling ke liye Swarm/Kubernetes chahiye (Chapter 09).
    07

    Security

    Default mein container ke andar process root (UID 0) se chalta hai. Agar attacker container ke andar code execution paa le (jaise koi vulnerable npm package), aur kahin container escape vulnerability bhi mil jaaye, root privileges ke saath host machine tak compromise ho sakta hai.

    RUN addgroup -g 1001 appgroup && adduser -u 1001 -G appgroup -D appuser
USER appuser          # ab is line ke baad ka sab kuch non-root user se
    docker run --read-only --tmpfs /tmp myimage
# filesystem read-only — malware/attacker kuch likh nahi sakta, sirf /tmp writable

    Real project mein use: Production Dockerfiles mein non-root user banana aur USER directive set karna standard security practice hai; --read-only stateless services (jaise pure API containers, no local writes) ke liye extra hardening layer hai.

    Galat tarika:

    ENV DB_PASSWORD=supersecret123   # NAHI — image ke andar permanently bake ho jaata hai

    ENV/ARG se set kiya gaya secret image layers mein hamesha ke liye save ho jaata hai — koi bhi docker history ya docker inspect se, ya image ko pull karke, secret plain text mein nikaal sakta hai, chahe baad mein wo variable "unset" bhi kar do.

    Sahi approaches

    • Runtime env injection — docker run -e ya --env-file (secrets image mein nahi, sirf running container ki memory mein).
    • Docker Secrets (Swarm) / Kubernetes Secrets — encrypted store, sirf runtime pe mount hote hain.
    • BuildKit secret mount (Chapter 02) — build-time secrets (jaise private npm token) bina image layer mein bake kiye use karna.
    • External secret managers — AWS Secrets Manager, HashiCorp Vault — app runtime pe fetch karta hai.
    trivy image myapp:1.0
# Base image ke known CVEs (vulnerabilities) list karta hai, severity ke saath

    Real project mein use: CI/CD pipeline mein docker build ke baad ek scan step add karte hain — agar HIGH/CRITICAL severity vulnerability mile, pipeline fail kar dete hain, image production tak push hi nahi hoti. Purani/unmaintained base images (jaise node:14) mein aksar known CVEs milte hain — isliye base images regularly update karna important hai.

    # Dikhne mein normal lagta hai (CI tools mein common pattern)
docker run -v /var/run/docker.sock:/var/run/docker.sock myimage

    Docker socket container ke andar mount karna matlab us container ko poore Docker daemon ka full control de dena — jo host pe root-equivalent access ke barabar hai. Agar us container mein koi bhi vulnerability ho, attacker socket ke through:

    • Naya privileged container spawn kar sakta hai jo host filesystem / ko mount kare.
    • Us naye container ke andar se seedha host ko control kar sakta hai — effectively container escape, bina kisi kernel exploit ke.

    Real project mein use: Jenkins/CI tools jo "Docker-in-Docker" ke liye socket mount karte hain, wahan yeh risk consciously accept kiya jaata hai (trusted CI environment mein) — lekin kabhi bhi untrusted/user-facing containers ko socket access mat do. Safer alternative: rootless Docker ya dedicated "Docker-in-Docker" sidecar with proper isolation.

    Quick Revision — Security Summary
    • Non-root user — USER directive, root se container escape ka blast radius kam karta hai.
    • Read-only filesystem — --read-only se runtime tampering rokta hai.
    • Secrets — kabhi ENV/ARG mein hardcode mat karo — image layers mein permanently store ho jaate hain; runtime injection ya secret manager use karo.
    • Image scanning — Trivy jaise tools CI/CD mein CVEs pakadte hain, vulnerable image ko production tak jaane se rokte hain.
    • Docker socket — container mein mount karna near-root access dena hai; sirf trusted CI context mein hi karo.

    Production Operations

    HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1

    docker ps mein container status healthy/unhealthy dikhata hai — orchestrators (Swarm/K8s) ise use karke traffic sirf healthy containers ko bhejte hain, aur unhealthy ko automatically restart/replace kar sakte hain.

    Graceful shutdown (app code mein)

    process.on('SIGTERM', () => {
  console.log('SIGTERM received — closing server gracefully');
  server.close(() => {
    mongoose.connection.close();
    process.exit(0);
  });
});

    Real project mein use: Bina isko handle kiye, docker stop pe app ko 10s ke andar hi seedha SIGKILL mil jaata hai, jisse in-flight requests aur DB transactions corrupt/incomplete reh sakte hain. SIGTERM handler existing requests complete hone dega, phir clean exit karega.

    Default json-file log driver disk pe unlimited grow kar sakta hai agar limit set na ho — ek chatty container mahino mein poora disk bhar sakta hai.

    docker run --log-opt max-size=10m --log-opt max-file=3 myimage
# har log file max 10MB, max 3 files rotate

    Real project mein use: Production mein logs ko container ke andar hi rakhne ke bajaye centralized logging (ELK stack, CloudWatch, Loki) mein bhejte hain — container delete ho jaaye toh bhi logs preserved rehte hain, aur multiple containers ke logs ek jagah search/correlate ho paate hain.

    Real incident: CI/CD pipeline har deploy pe naya image build karta hai, purani image untagged ho jaati hai (dangling) lekin disk pe reh jaati hai. Mahino baad, production server ka disk 95%+ full ho jaata hai, naye deploys fail hone lagte hain ("no space left on device"), aur kabhi-kabhi running containers bhi crash hone lagte hain.

    docker system df                  # kitni space kis cheez mein use ho rahi hai, dekho
docker image prune -a              # unused (dangling + untagged) images delete
docker volume prune                # kisi container se attached na hone wale volumes delete
docker system prune -a --volumes   # sab ek saath (careful — production mein soch samajh ke)
    Cautiondocker volume prune un named volumes ko bhi delete kar dega jo abhi kisi container se attached nahi hain lekin data important tha (jaise temporarily stopped DB container ka volume) — production mein blindly chalane se pehle zaroor check karo docker volume ls se.

    Prevention: CI/CD pipeline mein hi automated cleanup step (old images/builds prune) schedule karte hain, taaki manually intervene karne ki naubat hi na aaye.

    Naya container start karo, health check pass hone tak wait karo, tabhi purana container band karo — kabhi bhi "zero containers running" wala moment nahi aana chahiye.

    Blue-Green style single-host pattern 
    1. Naya container (v2) start karo — alag naam/port se
2. HEALTHCHECK pass hone tak wait karo
3. Load balancer (Nginx) ka upstream naye container (v2) pe point karo
4. Purana container (v1) ab traffic-free hai — safely stop karo

    Real project mein use: Single-host setups mein yeh manually/script se karte hain; multi-host/orchestrated setups (Swarm/K8s) mein rolling update yehi pattern built-in automate karke deta hai (Chapter 09).

    Same variable multiple jagah define ho sakta hai — Dockerfile, Compose file, ya CLI flag. Jo zyada specific / baad mein apply hota hai, wo jeetta hai:

    Priority (highest jeetega) 
    docker run -e VAR=x  (CLI, run-time)          ← highest priority
      ↑
docker-compose.yml "environment:"
      ↑
docker-compose.yml "env_file:"
      ↑
Dockerfile "ENV VAR=x"                        ← lowest priority (image default)

    Real project mein use: Dockerfile mein ENV NODE_ENV=production ek safe default set karte hain, lekin local dev/testing ke waqt docker run -e NODE_ENV=development se easily override kar dete hain — bina image rebuild kiye.

    Quick Revision — Production Ops Summary
    • HEALTHCHECK — container ki actual readiness batata hai; app mein SIGTERM handler graceful shutdown ke liye zaroori.
    • Logging — max-size/max-file se disk-fill se bachao; production mein centralized logging (ELK/CloudWatch).
    • Disk cleanup — docker system df se check, image/volume prune se cleanup; volume prune se pehle zaroor verify karo.
    • Zero-downtime — naya container healthy hone tak purana chalta rahe, phir switch.
    • ENV precedence — docker run -e > compose environment > env_file > Dockerfile ENV.

    Orchestration & CI/CD

    Dono multi-host container orchestration solve karte hain — scaling, self-healing, load balancing containers across multiple machines (jo single Docker/Compose nahi kar sakta).

    #Docker SwarmKubernetes (K8s)
    Setup complexitySimple — Docker mein hi built-inComplex — alag learning curve, zyada moving parts
    Feature setBasic (scaling, rolling update, service discovery)Bahut zyada advanced (auto-scaling, custom resources, huge ecosystem)
    Industry adoptionKam, chhote/simple projectsIndustry standard, large-scale production
    Kab useChhoti team, simple multi-host needs, fast setupLarge-scale, complex microservices, enterprise

    Interview line: "Real-world mein zyada tar companies Kubernetes use karti hain uske bade ecosystem (Helm, Operators, cloud-managed EKS/GKE/AKS) ki wajah se; Swarm simplicity ke liye chota use-case mein theek hai, lekin community/adoption Kubernetes ke mukable kaafi kam hai."

    # Bad — production mein kaunsa exact code chal raha hai, pata hi nahi
docker build -t myapp:latest .
docker push myapp:latest

# Good — git commit SHA ya semantic version se traceable
docker build -t myapp:$(git rev-parse --short HEAD) .
docker build -t myapp:v1.4.2 .

    Problem with :latest:

    • Not reproducible — "latest" ka matlab har build ke baad badal jaata hai; agar production issue aaye, exact pata nahi chalta kaunsa code version chal raha tha.
    • Rollback impossible — agar sirf :latest use kiya, purana version wapas laane ka koi seedha tareeka nahi (jab tak alag se track na kiya ho).
    • Accidental deploy risk — koi aur team member :latest push kar de, tumhara production khud-ba-khud unintended version pe chala jaaye (agar auto-pull configured hai).

    Real project mein use: CI/CD pipeline har build ko git commit SHA ya semver tag se tag karta hai; deployment configs (Compose/K8s manifests) usi specific tag ko reference karte hain — rollback matlab bas purana tag deploy karna, koi rebuild nahi.

    # CI/CD pipeline stages
docker build -t myregistry.com/myapp:$COMMIT_SHA .
docker push myregistry.com/myapp:$COMMIT_SHA

# Production server / orchestrator
docker pull myregistry.com/myapp:$COMMIT_SHA
docker service update --image myregistry.com/myapp:$COMMIT_SHA myapp   # Swarm example

# Rollback — bas purana tag wapas deploy karo
docker service update --image myregistry.com/myapp:$PREVIOUS_SHA myapp

    Real project mein use: Private registry (AWS ECR, GitLab Container Registry) mein saare tagged versions store rehte hain — production issue detect hote hi, naya code likhe bina, seconds mein purane working version pe rollback ho sakta hai.

    docker service scale myapp=5              # 5 instances chalao (Swarm)
docker service update --image myapp:v2 --update-parallelism 1 --update-delay 10s myapp

    Rolling update: Orchestrator ek-ek (ya batch) karke purane containers ko naye version se replace karta hai, har step ke beech health check verify karke — kabhi bhi saare instances ek saath down nahi hote (Nginx ke pm2 reload/graceful-reload concept jaisa hi hai, bas cluster-level pe).

    Scaling: Traffic badhne pe horizontal scaling — same image ke zyada replicas chala do, orchestrator khud load balance kar deta hai unke beech.

    Quick Revision — Orchestration & CI/CD Summary
    • Swarm vs Kubernetes — Swarm simple/built-in; K8s industry-standard, complex, feature-rich.
    • Tagging — :latest avoid karo production mein — git-SHA/semver se traceable, reproducible, rollback-friendly.
    • Registry — CI push karta hai, production pull karta hai; rollback = purana tag deploy karna.
    • Rolling updates — ek-ek batch karke replace, zero-downtime; scaling = replicas badhao, orchestrator load balance karta hai.
