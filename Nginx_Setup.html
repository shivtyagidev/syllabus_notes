01

Basics

Nginx (pronounced "engine-x") ek high-performance, open-source software hai jo 4 kaam kar sakta hai:

  • Web server — static files (HTML, CSS, JS, images) directly serve karta hai.
  • Reverse proxy — client ki request ko backend server (Node.js, Java, Python) tak forward karta hai.
  • Load balancer — ek se zyada backend servers ke beech traffic baant deta hai.
  • HTTP cache / SSL termination — response cache kar sakta hai, aur HTTPS certificate yahi handle karta hai taaki backend ko encryption ki tension na ho.

Real project mein: Node.js app (jo port 3000 pe chal raha hai) ke aage Nginx laga dete hain — users port 80/443 (Nginx) pe aate hain, Nginx andar se request ko Node app tak proxy kar deta hai.

Nginx Master-Worker process model pe chalta hai:

  • Master process — config file read karta hai, worker processes ko start/stop/reload karta hai, aur privileged kaam (jaise port 80 pe bind karna) khud karta hai. Yeh kabhi client requests directly handle nahi karta.
  • Worker processes — asli client requests yahi handle karte hain. Har worker single-threaded hota hai, lekin event-driven aur non-blocking (OS ka epoll/kqueue use karke) — isliye ek hi worker hazaaron concurrent connections ek saath handle kar leta hai, thread-per-request model ki tarah resource-heavy hue bina.
Master-Worker Model 
Master Process (config read, workers manage karta hai)
   │
   ├── Worker Process 1  (event loop — 1000s connections handle)
   ├── Worker Process 2  (event loop — 1000s connections handle)
   └── Worker Process N  (usually CPU cores ke barabar)

Yahi wajah hai ki Nginx bahut kam memory mein bhi C10k problem (10,000 concurrent connections) aasani se solve kar leta hai.

Nginx ka main config file nginx.conf hota hai (Linux mein usually /etc/nginx/nginx.conf), jo nested blocks { } mein likha jaata hai.

events {
  worker_connections 1024;      # ek worker kitne connections ek saath handle kare
}

http {
  include       mime.types;     # file extension ko sahi Content-Type se map karta hai
  sendfile      on;

  server {
    listen       80;                 # kis port pe yeh server sunega
    server_name  example.com;        # kis domain(s) ke liye yeh block match hoga

    root   /var/www/html;            # static files kahan se serve karni hain
    index  index.html index.htm;     # folder request pe default file

    location / {                     # '/' se shuru hone wale saare paths
      try_files $uri $uri/ =404;
    }

    location /api/ {                 # sirf '/api/' wale paths ke liye
      proxy_pass http://localhost:3000;  # Node.js backend ko reverse proxy
    }
  }
}

Nginx config nested contexts mein chalta hai, aur settings upar se neeche inherit hoti hain — jab tak koi zyada specific context khud apna override na de.

Hierarchy (Main → events/http → server → location) 
Main context (global — worker_processes, user, pid, error_log)
 ├── events { }
 └── http { }                    ← http-level defaults (saare servers ke liye)
       ├── server { }  (Site A)
       │     ├── location / { }
       │     └── location /api/ { }
       └── server { }  (Site B)
             └── location / { }

Inheritance rule: agar http {} block mein gzip on; likha hai, toh saare server{} blocks yeh setting automatically inherit kar lenge — jab tak koi specific server{} ya location{} khud gzip off; likh ke usko override na kare.

Priority (zyada specific jeetega): location > server > http > Main context.

Quick Revision — Nginx Basics Summary
  • Nginx — web server + reverse proxy + load balancer + SSL termination; Node app ke aage laga dete hain.
  • Architecture — ek Master process (config + workers manage) + kai Worker processes (event-driven, non-blocking, single-threaded, phir bhi 1000s connections handle).
  • Nginx vs Apache — Nginx event-driven/async (high concurrency mein better); Apache process/thread-per-connection, .htaccess support karta hai.
  • Install — apt install nginx (Ubuntu) / yum install nginx (CentOS) / Docker; verify nginx -v.
  • Commands — nginx -t (test), -s reload (no downtime), -s quit (graceful stop), -s stop (fast stop).
  • Config structure — events{} → http{} → server{} → location{}; directives: listen, server_name, root, index, include.
  • Config hierarchy — settings upar se neeche inherit hoti hain; location > server > http priority mein jeetta hai.
02

Reverse Proxy & Backend

Reverse proxy ek server hai jo client aur backend ke beech baith kar client ki request ko backend tak forward karta hai, aur backend ka response wapas client ko de deta hai. Client ko pata hi nahi chalta ki asli kaam kaun sa server kar raha hai — usse sirf Nginx dikhta hai.

Reverse Proxy Flow 
Client (browser)
    │  request → myshop.com
    ▼
Nginx (Reverse Proxy — port 80/443, public)
    │  forward → localhost:3000
    ▼
Backend (Node.js app — port 3000, sirf internal, kabhi public expose nahi)

Real project mein step-by-step kaam kaise karta hai

Maan lo ek e-commerce project hai: React frontend + Node.js backend (port 3000) + MongoDB, sab ek hi AWS/DigitalOcean server pe deployed hai, domain myshop.com hai. User browser mein myshop.com/api/products khola — step-by-step yeh hota hai:

  1. DNS lookup — browser myshop.com ko server ke public IP (jaise 65.2.10.5) mein resolve karta hai.
  2. Request server tak pahunchti hai — us IP pe sirf ek hi process port 80/443 pe listen kar raha hota hai — wo hai Nginx. Node.js app kabhi bhi is public IP/port pe directly nahi sunta.
  3. Nginx match karta hai — apni config mein server_name myshop.com aur location /api/ se match karke decide karta hai ki yeh request kahan bhejni hai.
  4. Internally forward hoti hai — proxy_pass http://localhost:3000/; ki wajah se Nginx usi machine ke andar hi (localhost, koi internet trip nahi) request ko Node app tak bhej deta hai, jo port 3000 pe internally sun raha tha.
  5. Backend apna kaam karta hai — Node app request ko normal Express route ki tarah handle karta hai, MongoDB se products fetch karta hai, JSON response taiyar karta hai.
  6. Response wapas Nginx se hoke jaata hai — Node app apna response Nginx ko deta hai, Nginx use client (browser) tak forward kar deta hai — client ko yeh pata hi nahi chalta ki beech mein Node.js tha, usse sirf myshop.com se response aaya dikhta hai.

Isi wajah se production mein firewall rule hoti hai: port 3000 sirf localhost se accessible ho, bahar se koi directly myshop.com:3000 hit hi nahi kar sakta — sirf Nginx (jo usi machine pe hai) usse baat kar sakta hai. Yeh reverse proxy ka sabse bada security benefit hai.

Isi example ko asli API se connect karke dekho — Frontend + Backend + Nginx

1) Frontend (React) — products list mangwane ke liye:

// src/App.jsx
function ProductList() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    // Note: sirf '/api/products' — koi domain/port nahi likha!
    // Kyunki frontend aur API dono "myshop.com" pe hi hain, browser khud current domain use kar lega
    fetch('/api/products')
      .then(res => res.json())
      .then(data => setProducts(data));
  }, []);

  return products.map(p => 
{p.name}
);
}

2) Nginx — is request ko pakad ke backend ko forward karta hai:

server {
  listen 80;
  server_name myshop.com;

  root /var/www/myshop/build;      # React build yahan se serve hoti hai
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;   # React app ke liye
  }

  location /api/ {
    proxy_pass http://localhost:3000/;  # '/api/products' → backend ko '/products' milega
  }
}

3) Backend (Node.js + Express) — port 3000 pe internally chal raha hai:

// server.js (localhost:3000 pe chal raha hai, kabhi public expose nahi)
const express = require('express');
const app = express();

app.get('/products', async (req, res) => {
  const products = await Product.find(); // MongoDB se data fetch
  res.json(products);
});

app.listen(3000, () => console.log('Backend running on port 3000'));

Poora connection samjho: Browser fetch('/api/products') call karta hai → yeh actually myshop.com/api/products pe jaata hai → Nginx location /api/ se match karke /api/ prefix hata ke sirf /products backend ko bhejta hai → Express ka app.get('/products', ...) route match hota hai → MongoDB se data leke JSON return karta hai → Nginx wahi response wapas browser ko de deta hai. Frontend ko backend ka port (3000) kabhi pata hi nahi chalta — usne sirf apne hi domain se ek relative URL call kiya.

Aur bhi real project mein use:

  • Security — backend (Node/Java app) kabhi directly internet pe expose nahi hota, sirf Nginx public hota hai; backend ka port firewall se block rehta hai.
  • SSL termination — HTTPS certificate sirf Nginx pe lagta hai, backend simple HTTP pe hi chalta rehta hai — certificate manage karna ek hi jagah.
  • Load balancing — ek hi Nginx, Node app ke 3-4 instances (port 3001, 3002, 3003) ke beech traffic baant sakta hai.
  • Multiple apps, ek hi domain — jaise myshop.com/ pe React app, myshop.com/api/ pe Node backend, myshop.com/admin/ pe alag admin app — sab alag services hone ke bawajood user ko ek hi domain dikhta hai.

proxy_pass directive batata hai ki request ko kahan forward karna hai — kis backend server/port pe.

location /api/ {
  proxy_pass http://localhost:3000/;   # yahan aane wali request Node app ko forward
}

Real project mein use: React frontend build folder root se serve hoti hai, aur /api/ se shuru hone wali sabhi requests (jaise /api/users, /api/orders) is directive se Node.js backend (port 3000) ko forward ho jaati hain.

Interview gotcha (trailing slash):

ConfigRequestBackend ko jaata hai
location /api/ { proxy_pass http://localhost:3000/; }/api/users/users (/api/ prefix hat gaya)
location /api/ { proxy_pass http://localhost:3000; }/api/users/api/users (poora path as-is gaya)

Yeh farq bahut common bug ka reason banta hai real projects mein — proxy_pass ke end mein / hai ya nahi, isse backend route match hoga ya 404 aayega.

Problem: Nginx jab request backend ko forward karta hai, backend ko lagta hai request Nginx se aa rahi hai (127.0.0.1) — asli client ka IP/domain/protocol kho jaata hai.

location /api/ {
  proxy_pass http://localhost:3000/;

  proxy_set_header Host $host;                            # original domain
  proxy_set_header X-Real-IP $remote_addr;                # client ka asli IP
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; # proxy chain ki IP list
  proxy_set_header X-Forwarded-Proto $scheme;              # http ya https
}
HeaderWithout (nahi set kiya toh)With (set karne pe)
HostBackend ko domain localhost dikhegaBackend ko asli domain (myshop.com) pata chalta hai
X-Real-IPSabka IP Nginx ka 127.0.0.1 dikhegaHar client ka apna real IP dikhta hai
X-Forwarded-ForPoori proxy chain ka pata nahi chaltaClient → CDN → Nginx, poori IP chain milti hai

Real example (login rate limiting): Rule hai — "1 IP se 5 galat password attempts ke baad block karo".

  • Without X-Real-IP — req.socket.remoteAddress saare users ke liye 127.0.0.1 deta hai → 1 attacker block hua matlab sabhi users block ho gaye.
  • With X-Real-IP — req.headers['x-real-ip'] har user ka apna real IP deta hai → sirf attacker block hota hai, baaki sab normally login karte hain.

Backend se response aane mein kitna time lagne dena hai, uske liye timeouts set karte hain — zyada lamba wait karna server resources block kar deta hai, bahut chhota timeout genuine slow requests ko todh deta hai.

proxy_connect_timeoutNginx ko backend se TCP connection banane mein kitna time lage

Real problem, step-by-step

Ek route hai /api/reports/generate jo DB se bahut saara data nikaal ke ek PDF report banata hai — isme 90 seconds lagte hain. Nginx ka proxy_read_timeout default 60 seconds hota hai. Kya hota hai:

  1. Client request bhejta hai /api/reports/generate pe.
  2. Nginx use backend ko forward karta hai, aur response ka wait karna shuru karta hai.
  3. Backend andar hi andar report generate karne mein busy hai (DB query + PDF banana chal raha hai).
  4. 60th second pe — Nginx ka dhairya khatam ho jaata hai, wo maan leta hai backend "mar gaya/atak gaya", aur client ko 504 Gateway Timeout bhej deta hai.
  5. Lekin backend ko yeh pata hi nahi ki Nginx ne client ko error de diya — wo abhi bhi kaam kar raha hai (30 seconds aur), aur report complete hone ke baad response bhejta hai jo kahin nahi jaata (client already error dekh chuka, connection band ho chuka) — server ka kaam waste gaya.
Timeline — kya galat hua 
0s -------------------- 60s -------- 90s
|                         |            |
Client request       Nginx timeout    Backend actually
bheja                (504 error       finish karta hai
                       client ko)     (par response waste — connection band ho chuka)

Fix — sirf usi slow route ke liye timeout badhao

Poore server ka timeout badhana galat approach hai — agar koi normal API (jaise /api/login) kabhi hang ho jaaye (backend bug, DB slow), toh Nginx use bhi 120 seconds tak pakde rahega, jisse ek slow request Nginx ka worker connection slot zyada der block karke rakhega. Isliye sirf us specific route ke liye alag location block banate hain:

server {
  # Normal APIs — default timeout theek hai (fast fail agar backend hang ho)
  location /api/ {
    proxy_pass http://localhost:3000/;
    proxy_read_timeout 30s;
  }

  # Sirf heavy report route ke liye — zyada time do
  location /api/reports/ {
    proxy_pass http://localhost:3000/reports/;
    proxy_read_timeout 120s;   # 90s se zyada, safe margin ke saath
  }
}

Nginx zyada specific location (/api/reports/) ko priority deta hai /api/ ke upar — isliye sirf report wala route hi lamba wait karega, baaki saari APIs pe fast-fail (30s) protection bana rahega.

Ek typical React frontend + Node.js backend project ka production Nginx config — upar wale saare concepts (reverse proxy, proxy_pass, headers, timeout) ek jagah:

server {
  listen 80;
  server_name myshop.com www.myshop.com;

  # 1) React frontend — static build seedhe Nginx hi serve karta hai
  root /var/www/myshop/build;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;   # React Router ke liye — SPA fallback
  }

  # 2) Node.js backend — /api/ wali requests reverse proxy se forward
  location /api/ {
    proxy_pass http://localhost:3000/;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 5s;
    proxy_read_timeout    30s;
  }
}

Isi ek config se: static frontend fast serve hota hai (Nginx directly), API calls Node backend ko forward hoti hain (client ka IP/domain preserve karte hue), aur slow backend routes ke liye timeout bhi control mein rehta hai.

Quick Revision — Reverse Proxy Summary
  • Reverse Proxy — client aur backend ke beech baithta hai; backend ko hide/protect karta hai, SSL/load-balancing ek jagah manage hoti hai.
  • proxy_pass — request ko backend server tak forward karta hai; trailing / se path prefix strip hota hai ya nahi, dhyan rakho.
  • proxy_set_header — backend ko original request info (Host, IP, protocol) bhejta hai, warna sab kho jaata hai.
  • X-Real-IP — client ka asli IP; X-Forwarded-For — poori proxy chain ki IP list.
  • Real use — in headers ke bina rate limiting/IP logging backend mein tootl jaati hai, kyunki sab requests Nginx ke IP se aati dikhengi.
  • Proxy Timeout (proxy_connect/send/read_timeout) — slow backend routes (jaise report generation) ko 504 Gateway Timeout se bachate hain.
  • Nginx + Backend — ek hi server block mein React static files + Node API reverse proxy dono ek saath common pattern hai.

Real scenario, step-by-step

Maan lo user ek public cafe wifi pe baith ke myshop.com pe login kar raha hai, username/password submit karta hai. Ek attacker usi wifi network pe hai aur traffic sniff kar raha hai (packet capture tool se):

  1. Without HTTPS (plain HTTP): Login request network pe plain text mein jaati hai — username=shiva&password=12345 jaisa data as-is readable hota hai. Attacker packet capture karke seedha password padh leta hai.
  2. With HTTPS: Wahi request encrypted bytes mein jaati hai (jaise a3f9e7...) — attacker packet capture toh kar sakta hai, lekin usme se actual password nikaal nahi sakta, kyunki sirf server ke paas hi decrypt karne ki key hoti hai.

Real project mein use: Login form, payment page, ya koi bhi sensitive data (password, card number) bhejne wala page hamesha HTTPS pe hona chahiye — isi wajah se.

SSL (Secure Sockets Layer) purana naam hai, TLS (Transport Layer Security) uska current/modern version hai — industry mein dono ko commonly "SSL" hi bola jaata hai.

Yeh protocol client aur server ke beech ek encrypted connection banata hai, taaki data transit mein safe rahe.

TLS Handshake (simplified) 
1. Client → Server: "Hello, HTTPS se connect karna hai"
2. Server → Client: apna SSL certificate bhejta hai (public key ke saath)
3. Client: certificate ko trusted CA list se verify karta hai
4. Client aur Server: ek shared "session key" secretly agree kar lete hain
5. Ab dono taraf ka data isi session key se encrypt/decrypt hota hai

Real project mein use: Jab bhi https://myshop.com khulta hai, browser aur server ke beech yeh poora handshake milliseconds mein ho jaata hai, uske baad hi actual page data (encrypted) transfer hota hai.

SSL certificate ek digital file hai jo prove karti hai ki ek domain ka asli owner kaun hai, aur usme server ki public key hoti hai. Isse ek trusted Certificate Authority (CA) issue karti hai (jaise Let's Encrypt, DigiCert).

Nginx ko HTTPS chalane ke liye 2 files chahiye:

  • Certificate (.crt / .pem) — public, domain aur CA ki details.
  • Private Key (.key) — secret, kabhi kisi ke saath share nahi karte, server pe hi rehti hai.
TypeVerification levelReal use
DV (Domain Validated)Bas domain ownership check hoti haiMost common, free (Let's Encrypt) — blogs, startups, small business sites

Real scenario — certificate na ho ya galat ho toh?

  • Without valid certificate: Browser ek bada "Your connection is not private" warning page dikhata hai, user ko "Proceed anyway" jaisa daravana option milta hai — 90%+ users yahin se site chhod dete hain. E-commerce ke liye yeh seedha sales loss hai.
  • With valid certificate: Browser chup-chaap padlock icon dikhata hai, user ko kuch pata hi nahi chalta ki peeche kitna kaam hua — site bilkul normally khulti hai.
server {
  listen 443 ssl;
  server_name myshop.com www.myshop.com;

  ssl_certificate     /etc/letsencrypt/live/myshop.com/fullchain.pem;  # certificate
  ssl_certificate_key /etc/letsencrypt/live/myshop.com/privkey.pem;    # private key

  root /var/www/myshop/build;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;
  }
}

Without yeh 2 lines (ssl_certificate / ssl_certificate_key) sahi set kiye — Nginx listen 443 ssl; pe start hi nahi hoga, config test (nginx -t) fail ho jaayega ("cannot load certificate" error).

With sahi paths — Nginx start hota hai, browser https://myshop.com pe request bhejta hai, Nginx apna certificate present karta hai, browser verify karke padlock dikhata hai.

Real project mein use: ssl_certificate aur ssl_certificate_key ka path Let's Encrypt (ya jis bhi CA se cert liya hai) ke diye gaye files ki taraf point karta hai.

Agar koi user galti se http://myshop.com type kare (bina s ke), toh use automatically HTTPS pe redirect kar dena chahiye, taaki wo kabhi bhi unencrypted connection pe na rahe.

server {
  listen 80;
  server_name myshop.com www.myshop.com;

  return 301 https://$host$request_uri;   # permanent redirect HTTP → HTTPS
}

Without is redirect ke — agar site HTTPS pe bhi ready hai, tab bhi jo user http://myshop.com type karega wo plain HTTP pe hi rahega (jab tak khud manually https:// na likhe) — matlab HTTPS lagane ka fayda uss user ko milega hi nahi.

With redirect — koi bhi http:// request aaye, Nginx turant 301 bhej deta hai, browser khud https://myshop.com pe dobara request karta hai — user ko pata bhi nahi chalta, wo seedha secure version pe pahunch jaata hai.

Real project mein use: Port 80 (HTTP) pe ek chhota sa server block sirf redirect ke liye rakhte hain; asli website 443 (HTTPS) wale server block mein serve hoti hai. 301 (permanent redirect) use karte hain taaki browsers/search engines ise yaad rakhein aur baar-baar redirect na maangein.

Let's Encrypt ek free, automated, open Certificate Authority hai — koi bhi domain ke liye free DV certificate issue karti hai (90 din valid).

Certbot Let's Encrypt ka official tool hai jo certificate obtain karna aur Nginx config khud update karna — dono automate kar deta hai.

# Certbot install karo (Nginx plugin ke saath)
sudo apt install certbot python3-certbot-nginx

# Certificate issue karo aur Nginx config khud-b-khud set karo
sudo certbot --nginx -d myshop.com -d www.myshop.com

Without Certbot (purana/manual tarika): paid CA se certificate khareedna, CSR (Certificate Signing Request) manually generate karna, files download karke server pe upload karna, Nginx config khud edit karna, aur redirect bhi khud likhna — sab manual, error-prone, aur paisa lagta hai.

With Certbot — sirf ek command: certbot --nginx -d myshop.com. Yeh khud hi certificate generate karta hai, ssl_certificate/ssl_certificate_key lines Nginx config mein add kar deta hai, aur HTTP→HTTPS redirect bhi khud set kar deta hai — upar ke 2 steps (config + redirect) manually likhne ki zaroorat hi nahi padti, aur bilkul free hai.

Real project mein use: Isi wajah se real projects mein certbot hi standard tarika hai — manual SSL setup ab bahut kam hota hai.

Let's Encrypt certificates sirf 90 din ke liye valid hote hain (security ke liye jaan-boojh kar short rakhe gaye hain) — agar renew na karo toh site achanak "Not Secure" ho jaati hai ya HTTPS completely break ho jaata hai.

# Renewal check karo (jinki expiry 30 din se kam bachi hai, wahi renew honge)
sudo certbot renew

# Bina asli renew kiye test karo ki renewal kaam karega ya nahi
sudo certbot renew --dry-run
Without auto-renewal vs With auto-renewal 
WITHOUT auto-renewal
  Day 1: Certificate issue hua (90 din valid)
  Day 90: Koi renew nahi kiya (bhool gaye)
  Day 91: Certificate EXPIRE — site achanak "Not Secure" / HTTPS error
          → production down, emergency fix karni padti hai, users trust khote hain

WITH auto-renewal (cron/systemd timer)
  Day 1: Certificate issue hua
  Har din 2 baar: 'certbot renew' khud check karta hai
  Day 60: "abhi 30 din se zyada bache hain" → kuch nahi karta
  Day 61: "ab 30 din se kam bache hain" → khud renew kar deta hai
  Day 91: Naya certificate pehle se active — koi downtime nahi

Real project mein use: Certbot install karte hi ek cron job / systemd timer khud-b-khud set ho jaata hai jo din mein 2 baar renewal check karta hai — isliye production mein manually kabhi renew yaad nahi rakhna padta, sab automatic hota hai. Interview mein zyada tar yehi pucha jaata hai: "agar site achanak HTTPS error dene lage toh sabse pehle kya check karoge?" — jawab: certbot certificates se expiry date check karo.

Quick Revision — SSL/HTTPS Summary
  • HTTP vs HTTPS — HTTPS encrypted (TLS) hai, port 443; HTTP plain text, port 80, MITM attack ka risk.
  • SSL/TLS — handshake ke through client-server ek encrypted connection banate hain; "SSL" aur "TLS" commonly same cheez ke liye bole jaate hain.
  • SSL Certificate — CA se milta hai, domain ownership + public key prove karta hai; Nginx ko certificate + private key dono chahiye.
  • HTTPS Config — listen 443 ssl; + ssl_certificate + ssl_certificate_key.
  • HTTP → HTTPS Redirect — port 80 wale server block mein return 301 https://$host$request_uri;.
  • Let's Encrypt — free automated CA; Certbot — certificate issue + Nginx config + redirect, sab ek command se automate karta hai.
  • SSL Renewal — Let's Encrypt certs 90 din valid; certbot renew aur auto-renewal cron/systemd timer se production mein manual kaam nahi karna padta.
