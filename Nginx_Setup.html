01

Basics

Nginx (pronounced "engine-x") ek high-performance, open-source software hai jo 4 kaam kar sakta hai:

  • Web server — static files (HTML, CSS, JS, images) directly serve karta hai.
  • Reverse proxy — client ki request ko backend server (Node.js, Java, Python) tak forward karta hai.
  • Load balancer — ek se zyada backend servers ke beech traffic baant deta hai.
  • HTTP cache / SSL termination — response cache kar sakta hai, aur HTTPS certificate yahi handle karta hai taaki backend ko encryption ki tension na ho.

Real project mein: Node.js app (jo port 3000 pe chal raha hai) ke aage Nginx laga dete hain — users port 80/443 (Nginx) pe aate hain, Nginx andar se request ko Node app tak proxy kar deta hai.

Nginx Master-Worker process model pe chalta hai:

  • Master process — config file read karta hai, worker processes ko start/stop/reload karta hai, aur privileged kaam (jaise port 80 pe bind karna) khud karta hai. Yeh kabhi client requests directly handle nahi karta.
  • Worker processes — asli client requests yahi handle karte hain. Har worker single-threaded hota hai, lekin event-driven aur non-blocking (OS ka epoll/kqueue use karke) — isliye ek hi worker hazaaron concurrent connections ek saath handle kar leta hai, thread-per-request model ki tarah resource-heavy hue bina.
Master-Worker Model 
Master Process (config read, workers manage karta hai)
   │
   ├── Worker Process 1  (event loop — 1000s connections handle)
   ├── Worker Process 2  (event loop — 1000s connections handle)
   └── Worker Process N  (usually CPU cores ke barabar)

Yahi wajah hai ki Nginx bahut kam memory mein bhi C10k problem (10,000 concurrent connections) aasani se solve kar leta hai.

Nginx ka main config file nginx.conf hota hai (Linux mein usually /etc/nginx/nginx.conf), jo nested blocks { } mein likha jaata hai.

events {
  worker_connections 1024;      # ek worker kitne connections ek saath handle kare
}

http {
  include       mime.types;     # file extension ko sahi Content-Type se map karta hai
  sendfile      on;

  server {
    listen       80;                 # kis port pe yeh server sunega
    server_name  example.com;        # kis domain(s) ke liye yeh block match hoga

    root   /var/www/html;            # static files kahan se serve karni hain
    index  index.html index.htm;     # folder request pe default file

    location / {                     # '/' se shuru hone wale saare paths
      try_files $uri $uri/ =404;
    }

    location /api/ {                 # sirf '/api/' wale paths ke liye
      proxy_pass http://localhost:3000;  # Node.js backend ko reverse proxy
    }
  }
}

Nginx config nested contexts mein chalta hai, aur settings upar se neeche inherit hoti hain — jab tak koi zyada specific context khud apna override na de.

Hierarchy (Main → events/http → server → location) 
Main context (global — worker_processes, user, pid, error_log)
 ├── events { }
 └── http { }                    ← http-level defaults (saare servers ke liye)
       ├── server { }  (Site A)
       │     ├── location / { }
       │     └── location /api/ { }
       └── server { }  (Site B)
             └── location / { }

Inheritance rule: agar http {} block mein gzip on; likha hai, toh saare server{} blocks yeh setting automatically inherit kar lenge — jab tak koi specific server{} ya location{} khud gzip off; likh ke usko override na kare.

Priority (zyada specific jeetega): location > server > http > Main context.

Quick Revision — Nginx Basics Summary
  • Nginx — web server + reverse proxy + load balancer + SSL termination; Node app ke aage laga dete hain.
  • Architecture — ek Master process (config + workers manage) + kai Worker processes (event-driven, non-blocking, single-threaded, phir bhi 1000s connections handle).
  • Nginx vs Apache — Nginx event-driven/async (high concurrency mein better); Apache process/thread-per-connection, .htaccess support karta hai.
  • Install — apt install nginx (Ubuntu) / yum install nginx (CentOS) / Docker; verify nginx -v.
  • Commands — nginx -t (test), -s reload (no downtime), -s quit (graceful stop), -s stop (fast stop).
  • Config structure — events{} → http{} → server{} → location{}; directives: listen, server_name, root, index, include.
  • Config hierarchy — settings upar se neeche inherit hoti hain; location > server > http priority mein jeetta hai.

Reverse Proxy & Backend

Reverse proxy ek server hai jo client aur backend ke beech baith kar client ki request ko backend tak forward karta hai, aur backend ka response wapas client ko de deta hai. Client ko pata hi nahi chalta ki asli kaam kaun sa server kar raha hai — usse sirf Nginx dikhta hai.

Reverse Proxy Flow 
Client (browser)
    │  request → myshop.com
    ▼
Nginx (Reverse Proxy — port 80/443, public)
    │  forward → localhost:3000
    ▼
Backend (Node.js app — port 3000, sirf internal, kabhi public expose nahi)

Real project mein step-by-step kaam kaise karta hai

Maan lo ek e-commerce project hai: React frontend + Node.js backend (port 3000) + MongoDB, sab ek hi AWS/DigitalOcean server pe deployed hai, domain myshop.com hai. User browser mein myshop.com/api/products khola — step-by-step yeh hota hai:

  1. DNS lookup — browser myshop.com ko server ke public IP (jaise 65.2.10.5) mein resolve karta hai.
  2. Request server tak pahunchti hai — us IP pe sirf ek hi process port 80/443 pe listen kar raha hota hai — wo hai Nginx. Node.js app kabhi bhi is public IP/port pe directly nahi sunta.
  3. Nginx match karta hai — apni config mein server_name myshop.com aur location /api/ se match karke decide karta hai ki yeh request kahan bhejni hai.
  4. Internally forward hoti hai — proxy_pass http://localhost:3000/; ki wajah se Nginx usi machine ke andar hi (localhost, koi internet trip nahi) request ko Node app tak bhej deta hai, jo port 3000 pe internally sun raha tha.
  5. Backend apna kaam karta hai — Node app request ko normal Express route ki tarah handle karta hai, MongoDB se products fetch karta hai, JSON response taiyar karta hai.
  6. Response wapas Nginx se hoke jaata hai — Node app apna response Nginx ko deta hai, Nginx use client (browser) tak forward kar deta hai — client ko yeh pata hi nahi chalta ki beech mein Node.js tha, usse sirf myshop.com se response aaya dikhta hai.

Isi wajah se production mein firewall rule hoti hai: port 3000 sirf localhost se accessible ho, bahar se koi directly myshop.com:3000 hit hi nahi kar sakta — sirf Nginx (jo usi machine pe hai) usse baat kar sakta hai. Yeh reverse proxy ka sabse bada security benefit hai.

Isi example ko asli API se connect karke dekho — Frontend + Backend + Nginx

1) Frontend (React) — products list mangwane ke liye:

// src/App.jsx
function ProductList() {
  const [products, setProducts] = useState([]);

  useEffect(() => {
    // Note: sirf '/api/products' — koi domain/port nahi likha!
    // Kyunki frontend aur API dono "myshop.com" pe hi hain, browser khud current domain use kar lega
    fetch('/api/products')
      .then(res => res.json())
      .then(data => setProducts(data));
  }, []);

  return products.map(p => 
{p.name}
);
}

2) Nginx — is request ko pakad ke backend ko forward karta hai:

server {
  listen 80;
  server_name myshop.com;

  root /var/www/myshop/build;      # React build yahan se serve hoti hai
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;   # React app ke liye
  }

  location /api/ {
    proxy_pass http://localhost:3000/;  # '/api/products' → backend ko '/products' milega
  }
}

3) Backend (Node.js + Express) — port 3000 pe internally chal raha hai:

// server.js (localhost:3000 pe chal raha hai, kabhi public expose nahi)
const express = require('express');
const app = express();

app.get('/products', async (req, res) => {
  const products = await Product.find(); // MongoDB se data fetch
  res.json(products);
});

app.listen(3000, () => console.log('Backend running on port 3000'));

Poora connection samjho: Browser fetch('/api/products') call karta hai → yeh actually myshop.com/api/products pe jaata hai → Nginx location /api/ se match karke /api/ prefix hata ke sirf /products backend ko bhejta hai → Express ka app.get('/products', ...) route match hota hai → MongoDB se data leke JSON return karta hai → Nginx wahi response wapas browser ko de deta hai. Frontend ko backend ka port (3000) kabhi pata hi nahi chalta — usne sirf apne hi domain se ek relative URL call kiya.

Aur bhi real project mein use:

  • Security — backend (Node/Java app) kabhi directly internet pe expose nahi hota, sirf Nginx public hota hai; backend ka port firewall se block rehta hai.
  • SSL termination — HTTPS certificate sirf Nginx pe lagta hai, backend simple HTTP pe hi chalta rehta hai — certificate manage karna ek hi jagah.
  • Load balancing — ek hi Nginx, Node app ke 3-4 instances (port 3001, 3002, 3003) ke beech traffic baant sakta hai.
  • Multiple apps, ek hi domain — jaise myshop.com/ pe React app, myshop.com/api/ pe Node backend, myshop.com/admin/ pe alag admin app — sab alag services hone ke bawajood user ko ek hi domain dikhta hai.

proxy_pass directive batata hai ki request ko kahan forward karna hai — kis backend server/port pe.

location /api/ {
  proxy_pass http://localhost:3000/;   # yahan aane wali request Node app ko forward
}

Real project mein use: React frontend build folder root se serve hoti hai, aur /api/ se shuru hone wali sabhi requests (jaise /api/users, /api/orders) is directive se Node.js backend (port 3000) ko forward ho jaati hain.

Interview gotcha (trailing slash):

ConfigRequestBackend ko jaata hai
location /api/ { proxy_pass http://localhost:3000/; }/api/users/users (/api/ prefix hat gaya)
location /api/ { proxy_pass http://localhost:3000; }/api/users/api/users (poora path as-is gaya)

Yeh farq bahut common bug ka reason banta hai real projects mein — proxy_pass ke end mein / hai ya nahi, isse backend route match hoga ya 404 aayega.

Problem: Nginx jab request backend ko forward karta hai, backend ko lagta hai request Nginx se aa rahi hai (127.0.0.1) — asli client ka IP/domain/protocol kho jaata hai.

location /api/ {
  proxy_pass http://localhost:3000/;

  proxy_set_header Host $host;                            # original domain
  proxy_set_header X-Real-IP $remote_addr;                # client ka asli IP
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; # proxy chain ki IP list
  proxy_set_header X-Forwarded-Proto $scheme;              # http ya https
}
HeaderWithout (nahi set kiya toh)With (set karne pe)

X-Real-IPSabka IP Nginx ka 127.0.0.1 dikhegaHar client ka apna real IP dikhta hai
X-Forwarded-ForPoori proxy chain ka pata nahi chaltaClient → CDN → Nginx, poori IP chain milti hai

Real example (login rate limiting): Rule hai — "1 IP se 5 galat password attempts ke baad block karo".

  • Without X-Real-IP — req.socket.remoteAddress saare users ke liye 127.0.0.1 deta hai → 1 attacker block hua matlab sabhi users block ho gaye.
  • With X-Real-IP — req.headers['x-real-ip'] har user ka apna real IP deta hai → sirf attacker block hota hai, baaki sab normally login karte hain.

Backend se response aane mein kitna time lagne dena hai, uske liye timeouts set karte hain — zyada lamba wait karna server resources block kar deta hai, bahut chhota timeout genuine slow requests ko todh deta hai.

Real problem, step-by-step

Ek route hai /api/reports/generate jo DB se bahut saara data nikaal ke ek PDF report banata hai — isme 90 seconds lagte hain. Nginx ka proxy_read_timeout default 60 seconds hota hai. Kya hota hai:

  1. Client request bhejta hai /api/reports/generate pe.
  2. Nginx use backend ko forward karta hai, aur response ka wait karna shuru karta hai.
  3. Backend andar hi andar report generate karne mein busy hai (DB query + PDF banana chal raha hai).
  4. 60th second pe — Nginx ka dhairya khatam ho jaata hai, wo maan leta hai backend "mar gaya/atak gaya", aur client ko 504 Gateway Timeout bhej deta hai.
  5. Lekin backend ko yeh pata hi nahi ki Nginx ne client ko error de diya — wo abhi bhi kaam kar raha hai (30 seconds aur), aur report complete hone ke baad response bhejta hai jo kahin nahi jaata (client already error dekh chuka, connection band ho chuka) — server ka kaam waste gaya.
Timeline — kya galat hua 
0s -------------------- 60s -------- 90s
|                         |            |
Client request       Nginx timeout    Backend actually
bheja                (504 error       finish karta hai
                       client ko)     (par response waste — connection band ho chuka)

Fix — sirf usi slow route ke liye timeout badhao

Poore server ka timeout badhana galat approach hai — agar koi normal API (jaise /api/login) kabhi hang ho jaaye (backend bug, DB slow), toh Nginx use bhi 120 seconds tak pakde rahega, jisse ek slow request Nginx ka worker connection slot zyada der block karke rakhega. Isliye sirf us specific route ke liye alag location block banate hain:

server {
  # Normal APIs — default timeout theek hai (fast fail agar backend hang ho)
  location /api/ {
    proxy_pass http://localhost:3000/;
    proxy_read_timeout 30s;
  }

  # Sirf heavy report route ke liye — zyada time do
  location /api/reports/ {
    proxy_pass http://localhost:3000/reports/;
    proxy_read_timeout 120s;   # 90s se zyada, safe margin ke saath
  }
}

Nginx zyada specific location (/api/reports/) ko priority deta hai /api/ ke upar — isliye sirf report wala route hi lamba wait karega, baaki saari APIs pe fast-fail (30s) protection bana rahega.

Ek typical React frontend + Node.js backend project ka production Nginx config — upar wale saare concepts (reverse proxy, proxy_pass, headers, timeout) ek jagah:

server {
  listen 80;
  server_name myshop.com www.myshop.com;

  # 1) React frontend — static build seedhe Nginx hi serve karta hai
  root /var/www/myshop/build;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;   # React Router ke liye — SPA fallback
  }

  # 2) Node.js backend — /api/ wali requests reverse proxy se forward
  location /api/ {
    proxy_pass http://localhost:3000/;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 5s;
    proxy_read_timeout    30s;
  }
}

Isi ek config se: static frontend fast serve hota hai (Nginx directly), API calls Node backend ko forward hoti hain (client ka IP/domain preserve karte hue), aur slow backend routes ke liye timeout bhi control mein rehta hai.

Quick Revision — Reverse Proxy Summary
  • Reverse Proxy — client aur backend ke beech baithta hai; backend ko hide/protect karta hai, SSL/load-balancing ek jagah manage hoti hai.
  • proxy_pass — request ko backend server tak forward karta hai; trailing / se path prefix strip hota hai ya nahi, dhyan rakho.
  • proxy_set_header — backend ko original request info (Host, IP, protocol) bhejta hai, warna sab kho jaata hai.
  • X-Real-IP — client ka asli IP; X-Forwarded-For — poori proxy chain ki IP list.
  • Real use — in headers ke bina rate limiting/IP logging backend mein tootl jaati hai, kyunki sab requests Nginx ke IP se aati dikhengi.
  • Proxy Timeout (proxy_connect/send/read_timeout) — slow backend routes (jaise report generation) ko 504 Gateway Timeout se bachate hain.
  • Nginx + Backend — ek hi server block mein React static files + Node API reverse proxy dono ek saath common pattern hai.

Phase 3 — SSL / HTTPS

Poora Concept Ek Saath — Simple Flow (Segregated)

1. Problem: Normal HTTP (port 80) mein data plain text mein jaata hai — koi bhi beech mein baithke (jaise cafe wifi pe) password/card number seedha padh sakta hai. Browser aise site ko "Not Secure" bhi dikhata hai.

2. Solution — HTTPS: HTTPS (port 443) wahi data SSL/TLS se encrypt (lock) karke bhejta hai. SSL purana naam hai, TLS current version — dono ko commonly "SSL" hi bolte hain. Browser padlock 🔒 dikhata hai aur Google bhi HTTPS sites ko rank mein priority deta hai.

#HTTPHTTPS
DataPlain textEncrypted (TLS)
Port80443
Browser"Not Secure" warningPadlock icon

3. Lock kaise lagta hai — TLS Handshake: Browser aur server milke ek secret "session key" set karte hain, uske baad saara data usi key se encrypt/decrypt hota hai:

1. Client → Server: "HTTPS se connect karna hai"
2. Server → Client: apna SSL certificate bhejta hai (public key ke saath)
3. Client: certificate ko trusted CA list se verify karta hai
4. Client + Server: ek shared "session key" secretly agree karte hain
5. Ab dono taraf ka data isi key se encrypt/decrypt hota hai

4. Certificate kya hai: Ek digital "ID card" jo prove karta hai domain ka asli owner kaun hai — ek trusted Certificate Authority (CA) (jaise Let's Encrypt) issue karti hai. Nginx ko 2 files chahiye: Certificate (.crt/.pem — public) aur Private Key (.key — secret, kabhi share nahi karte).

5. Nginx mein config kaise: Server block ko 443 pe SSL ke saath sunna hota hai, aur certificate + key ka path dena hota hai:

server {
  listen 443 ssl;
  server_name myshop.com;
  ssl_certificate     /etc/letsencrypt/live/myshop.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/myshop.com/privkey.pem;
}

6. Purane HTTP users ko redirect karna: Agar koi http://myshop.com type kare, use automatically https:// pe bhej dete hain — port 80 wale server block mein bas ek line:

server {
  listen 80;
  server_name myshop.com;
  return 301 https://$host$request_uri;
}

7. Certificate practically kaise milta hai: Let's Encrypt ek free CA hai, aur Certbot uska official tool hai jo sab kuch ek hi command mein automate kar deta hai — certificate issue, Nginx config (point 5), aur redirect (point 6) teeno khud kar deta hai:

sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d myshop.com -d www.myshop.com

8. Maintenance — Renewal: Let's Encrypt certificates sirf 90 din valid hote hain. Certbot install hote hi ek auto cron/systemd timer khud set ho jaata hai jo din mein 2 baar check karta hai aur expiry se 30 din pehle khud renew kar deta hai — isliye production mein manually kabhi renew yaad nahi rakhna padta.

Ek line mein poora flow: HTTP insecure hai (plain text) → HTTPS use karo (SSL/TLS se encrypt) → iske liye certificate chahiye (CA issue karti hai) → Nginx mein listen 443 ssl + cert paths daalo → port 80 se 443 pe redirect bhi karo → ye sab Certbot ek command mein free mein kar deta hai → aur khud hi renew bhi karta rehta hai.

Simple bhasha mein: HTTP mein tumhara data (jaise login ka username/password) plain text mein jaata hai — jaise postcard pe likha message, jise raaste mein koi bhi khol ke padh sakta hai. HTTPS mein wahi data encrypt (lock) karke jaata hai — jaise sealed envelope, jise sirf server hi khol (decrypt kar) sakta hai. Beech mein koi attacker packet pakad bhi le, use sirf ulta-seedha code dikhega, asli password nahi.

http:// = port 80, koi lock nahi, browser "Not Secure" dikhata hai. https:// = port 443, S matlab Secure, browser padlock 🔒 dikhata hai.

Real scenario, step-by-step

Maan lo user ek public cafe wifi pe baith ke myshop.com pe login kar raha hai, username/password submit karta hai. Ek attacker usi wifi network pe hai aur traffic sniff kar raha hai (packet capture tool se):

  1. Without HTTPS (plain HTTP): Login request network pe plain text mein jaati hai — username=shiva&password=12345 jaisa data as-is readable hota hai. Attacker packet capture karke seedha password padh leta hai.
  2. With HTTPS: Wahi request encrypted bytes mein jaati hai (jaise a3f9e7...) — attacker packet capture toh kar sakta hai, lekin usme se actual password nikaal nahi sakta, kyunki sirf server ke paas hi decrypt karne ki key hoti hai.

Real project mein use: Login form, payment page, ya koi bhi sensitive data (password, card number) bhejne wala page hamesha HTTPS pe hona chahiye — isi wajah se.

SSL (Secure Sockets Layer) purana naam hai, TLS (Transport Layer Security) uska current/modern version hai — industry mein dono ko commonly "SSL" hi bola jaata hai.

Yeh protocol client aur server ke beech ek encrypted connection banata hai, taaki data transit mein safe rahe.

TLS Handshake (simplified) 
1. Client → Server: "Hello, HTTPS se connect karna hai"
2. Server → Client: apna SSL certificate bhejta hai (public key ke saath)
3. Client: certificate ko trusted CA list se verify karta hai
4. Client aur Server: ek shared "session key" secretly agree kar lete hain
5. Ab dono taraf ka data isi session key se encrypt/decrypt hota hai

Real project mein use: Jab bhi https://myshop.com khulta hai, browser aur server ke beech yeh poora handshake milliseconds mein ho jaata hai, uske baad hi actual page data (encrypted) transfer hota hai.

SSL certificate ek digital file hai jo prove karti hai ki ek domain ka asli owner kaun hai, aur usme server ki public key hoti hai. Isse ek trusted Certificate Authority (CA) issue karti hai (jaise Let's Encrypt, DigiCert).

Nginx ko HTTPS chalane ke liye 2 files chahiye:

  • Certificate (.crt / .pem) — public, domain aur CA ki details.
  • Private Key (.key) — secret, kabhi kisi ke saath share nahi karte, server pe hi rehti hai.

Real scenario — certificate na ho ya galat ho toh?

  • Without valid certificate: Browser ek bada "Your connection is not private" warning page dikhata hai, user ko "Proceed anyway" jaisa daravana option milta hai — 90%+ users yahin se site chhod dete hain. E-commerce ke liye yeh seedha sales loss hai.
  • With valid certificate: Browser chup-chaap padlock icon dikhata hai, user ko kuch pata hi nahi chalta ki peeche kitna kaam hua — site bilkul normally khulti hai.
server {
  listen 443 ssl;
  server_name myshop.com www.myshop.com;

  ssl_certificate     /etc/letsencrypt/live/myshop.com/fullchain.pem;  # certificate
  ssl_certificate_key /etc/letsencrypt/live/myshop.com/privkey.pem;    # private key

  root /var/www/myshop/build;
  index index.html;

  location / {
    try_files $uri $uri/ /index.html;
  }
}

Without yeh 2 lines (ssl_certificate / ssl_certificate_key) sahi set kiye — Nginx listen 443 ssl; pe start hi nahi hoga, config test (nginx -t) fail ho jaayega ("cannot load certificate" error).

With sahi paths — Nginx start hota hai, browser https://myshop.com pe request bhejta hai, Nginx apna certificate present karta hai, browser verify karke padlock dikhata hai.

Real project mein use: ssl_certificate aur ssl_certificate_key ka path Let's Encrypt (ya jis bhi CA se cert liya hai) ke diye gaye files ki taraf point karta hai.

Agar koi user galti se http://myshop.com type kare (bina s ke), toh use automatically HTTPS pe redirect kar dena chahiye, taaki wo kabhi bhi unencrypted connection pe na rahe.

server {
  listen 80;
  server_name myshop.com www.myshop.com;

  return 301 https://$host$request_uri;   # permanent redirect HTTP → HTTPS
}

Without is redirect ke — agar site HTTPS pe bhi ready hai, tab bhi jo user http://myshop.com type karega wo plain HTTP pe hi rahega (jab tak khud manually https:// na likhe) — matlab HTTPS lagane ka fayda uss user ko milega hi nahi.

With redirect — koi bhi http:// request aaye, Nginx turant 301 bhej deta hai, browser khud https://myshop.com pe dobara request karta hai — user ko pata bhi nahi chalta, wo seedha secure version pe pahunch jaata hai.

Real project mein use: Port 80 (HTTP) pe ek chhota sa server block sirf redirect ke liye rakhte hain; asli website 443 (HTTPS) wale server block mein serve hoti hai. 301 (permanent redirect) use karte hain taaki browsers/search engines ise yaad rakhein aur baar-baar redirect na maangein.

Let's Encrypt ek free, automated, open Certificate Authority hai — koi bhi domain ke liye free DV certificate issue karti hai (90 din valid).

Certbot Let's Encrypt ka official tool hai jo certificate obtain karna aur Nginx config khud update karna — dono automate kar deta hai.

# Certbot install karo (Nginx plugin ke saath)
sudo apt install certbot python3-certbot-nginx

# Certificate issue karo aur Nginx config khud-b-khud set karo
sudo certbot --nginx -d myshop.com -d www.myshop.com

Without Certbot (purana/manual tarika): paid CA se certificate khareedna, CSR (Certificate Signing Request) manually generate karna, files download karke server pe upload karna, Nginx config khud edit karna, aur redirect bhi khud likhna — sab manual, error-prone, aur paisa lagta hai.

With Certbot — sirf ek command: certbot --nginx -d myshop.com. Yeh khud hi certificate generate karta hai, ssl_certificate/ssl_certificate_key lines Nginx config mein add kar deta hai, aur HTTP→HTTPS redirect bhi khud set kar deta hai — upar ke 2 steps (config + redirect) manually likhne ki zaroorat hi nahi padti, aur bilkul free hai.

Real project mein use: Isi wajah se real projects mein certbot hi standard tarika hai — manual SSL setup ab bahut kam hota hai.

Let's Encrypt certificates sirf 90 din ke liye valid hote hain (security ke liye jaan-boojh kar short rakhe gaye hain) — agar renew na karo toh site achanak "Not Secure" ho jaati hai ya HTTPS completely break ho jaata hai.

# Renewal check karo (jinki expiry 30 din se kam bachi hai, wahi renew honge)
sudo certbot renew

# Bina asli renew kiye test karo ki renewal kaam karega ya nahi
sudo certbot renew --dry-run

Interview mein zyada tar yehi pucha jaata hai: "agar site achanak HTTPS error dene lage toh sabse pehle kya check karoge?" — jawab: certbot certificates se expiry date check karo.

Quick Revision — SSL/HTTPS Summary
  • HTTP vs HTTPS — HTTPS encrypted (TLS) hai, port 443; HTTP plain text, port 80, MITM attack ka risk.
  • SSL/TLS — handshake ke through client-server ek encrypted connection banate hain; "SSL" aur "TLS" commonly same cheez ke liye bole jaate hain.
  • SSL Certificate — CA se milta hai, domain ownership + public key prove karta hai; Nginx ko certificate + private key dono chahiye.
  • HTTPS Config — listen 443 ssl; + ssl_certificate + ssl_certificate_key.
  • HTTP → HTTPS Redirect — port 80 wale server block mein return 301 https://$host$request_uri;.
  • Let's Encrypt — free automated CA; Certbot — certificate issue + Nginx config + redirect, sab ek command se automate karta hai.
  • SSL Renewal — Let's Encrypt certs 90 din valid; certbot renew aur auto-renewal cron/systemd timer se production mein manual kaam nahi karna padta.

Phase 4 — Load Balancing

Poora Concept Ek Saath — Simple Flow

1. Problem: Agar tumhara pura traffic ek hi backend server (jaise localhost:3000) pe jaa raha hai, toh high traffic mein wo overload ho jaata hai — slow ho jaata hai ya crash kar jaata hai. Yeh ek single point of failure hai.

2. Solution — Load Balancing: Ek hi app ke multiple copies (instances) alag-alag ports pe chalao (jaise 3001, 3002, 3003), aur Nginx ko load balancer bana do — wo incoming traffic ko in sab servers ke beech baant deta hai.

3. upstream block: Sabse pehle sab backend servers ko ek naam ke group mein list karte hain, fir proxy_pass ko seedha backend ke bajaye isi group ke naam pe point karte hain — yeh bina hota toh sara traffic ek hi proxy_pass http://localhost:3000; pe jaata, spike aane pe wahi ek server crash karta aur poori site down ho jaati:

upstream backend_servers {
  server localhost:3001;
  server localhost:3002;
  server localhost:3003;
}

server {
  listen 80;
  location / {
    proxy_pass http://backend_servers;   # seedha port nahi, upstream group ka naam
  }
}

Real project mein use: Node app ke PM2 cluster mode ya multiple Docker containers ke instances ko ek upstream group mein daal ke Nginx ke peeche laga dete hain.

4. Round Robin (default algorithm): Koi algorithm specify na karo toh Nginx turn-wise, sequential order mein requests bhejta hai:

Round Robin Flow 
Request 1 → server1 (3001)
Request 2 → server2 (3002)
Request 3 → server3 (3003)
Request 4 → server1 (3001)   ← wapas shuru se
Request 5 → server2 (3002) ...

Yeh maan ke chalta hai ki sab servers ki capacity barabar hai. Real project mein use: Jab sab instances same specs pe same tarah ki requests handle karte hon (simple REST API) — best/simplest choice, bina kuch configure kiye equal distribution.

5. Weighted Load Balancing: Agar ek server dusre se zyada powerful hai (zyada RAM/CPU), toh use weight de do — usko proportionally zyada requests milengi:

upstream backend_servers {
  server localhost:3001 weight=3;   # har 4 requests mein se 3 isko
  server localhost:3002 weight=1;   # ...aur 1 isko
}

Bina weight ke (plain Round Robin): agar server1 ek 8-core powerful machine hai aur server2 sirf 2-core chhoti machine, phir bhi dono ko barabar requests milti hain — server2 jaldi overload ho jaata hai jabki server1 idle padha rehta hai. Weight de ke resources ka sahi use hota hai. Real project mein use: mixed hardware, ya canary deployment (naye version wale server ko pehle kam weight de ke slowly traffic badhaana).

6. Least Connections: Har request same time nahi leti — agar Round Robin turn ke hisaab se server1 ko ek heavy request (bada file upload, 10 sec) mil gayi, toh turn ke hisaab se usko agli requests bhi milti rahengi aur wo jaam ho jaata hai, jabki server2 free baitha rehta hai. least_conn lagate hi Nginx real-time mein check karta hai kis server pe abhi sabse kam active connections hain, aur nayi request wahi bhejta hai:

upstream backend_servers {
  least_conn;
  server localhost:3001;
  server localhost:3002;
}

Real project mein use: jab requests ka processing time vary karta hai (kuch fast APIs, kuch slow reports/uploads) — Round Robin se better.

7. IP Hash: Round robin/least_conn mein ek hi client ki alag-alag requests alag-alag servers pe ja sakti hain. Agar login session server ki memory mein store ho raha hai (Redis/DB mein shared nahi), toh problem hai — login request server1 pe gayi aur session wahin save hua, lekin agli request ("profile dekho") server2 pe chali gayi jise pata hi nahi user login hai — user ko dobara login maanga jaata hai. ip_hash client ke IP ka hash nikaal ke use hamesha usi server pe bhejta hai, isliye session wala issue nahi hota:

upstream backend_servers {
  ip_hash;
  server localhost:3001;
  server localhost:3002;
}

Real project mein use: jab session local memory mein store hota hai. Better/modern fix: shared session store (Redis) use karo, phir ip_hash ki zaroorat hi nahi padti aur load balancing fully flexible rehti hai.

8. Backend Failure Handling: Agar koi backend server down/crash ho jaaye aur Nginx ko pata na ho, toh wo turn ke hisaab se usi crashed server ko request bhejta rahega aur users ko 500/502 errors milte rahenge. Isse bachne ke liye Nginx server ki health track karta hai aur failing server ko thodi der ke liye skip kar deta hai:

upstream backend_servers {
  server localhost:3001 max_fails=3 fail_timeout=30s;
  server localhost:3002 max_fails=3 fail_timeout=30s;
  server localhost:3003 backup;   # baaki sab down ho tabhi yeh use hoga
}
DirectiveMatlab
max_fails=3Lagatar 3 baar fail hone par server ko "down" maan lo
fail_timeout=30sAgle 30 sec us server ko traffic mat bhejo, phir dobara try karo
backupSirf tab use hota hai jab baaki saare servers down ho jaayein

Real project mein use: Production mein yeh hamesha set karte hain — bina iske ek crashed server poore system ko intermittently broken dikha sakta hai; iske saath user ko pata hi nahi chalta peeche ek server down tha (zero downtime unke perspective se).

Ek line mein poora flow (yaad rakhne ke liye): Ek server overload/single-point-of-failure hai → multiple instances chalao aur upstream group banao → default Round Robin se traffic baant jaata hai → alag capacity ho toh weight do → alag processing time ho toh least_conn use karo → session sticky chahiye toh ip_hash → aur koi server crash ho jaaye toh max_fails/fail_timeout/backup se Nginx use khud skip kar deta hai.

Phase 5 — Static Files

Poora Concept Ek Saath — Simple Flow

0. Bada picture: npm run build se React/Angular ka dist/ folder banta hai (plain HTML/CSS/JS). Nginx / pages seedha dist/ se, aur /api/... Node backend ko forward karta hai. Real use: ek hi Nginx, do kaam — static fast serve + dynamic API proxy.

location /       { root /var/www/myshop/dist; try_files $uri $uri/ /index.html; }  # static
location /api/   { proxy_pass http://localhost:3000/; }                            # dynamic

1. Static File Serving: HTML/CSS/JS/images change nahi hoti → Nginx seedha disk se deta hai, Node tak jaane ki zaroorat nahi (fast, no JS processing). Real use: React/Angular dist/, images, PDFs Nginx serve karta hai; Node sirf /api/* sambhalta hai.

root  /var/www/myshop/dist;
index index.html;
location / { try_files $uri $uri/ =404; }

2. root vs alias: root location path aage jodta hai; alias use replace kar deta hai. alias mein trailing / bhoolna → 404.

#rootalias

Exampleroot /var/www; → /images/cat.png → /var/www/images/cat.pngalias /var/www/pics/; → /images/cat.png → /var/www/pics/cat.png

Real use: URL folder naam disk folder se match na kare tab alias; warna root hi kaafi.

3. try_files: Order mein check karta hai, pehla match serve karta hai:

try_files $uri $uri/ /index.html;
# $uri → exact file, $uri/ → folder, /index.html → fallback

Real use: static sites + SPA routing (agla point) — bina iske seedha 404.

4. Angular/React SPA Deployment: SPA routing (/about) client-side JS mein hoti hai, server pe file exist nahi — bina fallback ke refresh pe 404. Fallback lagate hi index.html serve hota hai, phir JS apna router chalake page dikha deta hai:

location / { try_files $uri $uri/ /index.html; }   # SPA fix
location /api/ { proxy_pass http://localhost:3000/; }

Real use: Har React/Angular/Vue production deployment mein zaroori — warna direct URL/refresh 404 dega.

5. Static Caching: Rarely-changing files ko browser mein lambe time tak cache karwate hain — fast repeat loads:

location ~* \.(js|css|png|jpg|svg|woff2)$ {
  expires 30d;
  add_header Cache-Control "public, immutable";
}

Problem: file update hone par bhi browser 30 din tak purana cached JS use karta rehta hai. Fix: build tool filename mein content hash jodta hai (app.a3f9e7.js) — naya build = naya naam = purani cache kabhi use nahi hoti. Real use: Vite/CRA/Angular build khud hashed filenames generate karte hain, manually kuch nahi karna padta.

Ek line mein poora flow: dist/ se static, /api/ se backend → static root/index se serve → path ke liye root (append) ya alias (replace) → try_files order-fallback → SPA mein yehi fallback index.html pe jaata hai (routing todne se bachata) → static assets cache karte hain + hashed filenames se stale-cache fix.

Phase 6 — Performance

Real Scenario — Diwali Sale Traffic (Sab Terms Ek Kahani Mein)

myshop.com pe Diwali sale ka din, achanak 5000 users ek saath aa gaye:

  • Server start: Machine mein 4 CPU cores → worker_processes auto; se Nginx 4 worker processes banata hai, ek-ek core ke liye.
  • Traffic peak: Har worker worker_connections 1024; ke hisaab se 1024 connections sambhalta hai → 4 × 1024 = ~4096 users ek saath serve ho sakte hain.
  • Homepage khulta hai: Ek page ki 15-20 requests (HTML/CSS/JS/images) ke liye keepalive_timeout 65; se ek hi TCP connection reuse hota hai — page fast khulta hai; Nginx↔backend ke beech bhi keepalive 32; se connections reuse hote hain.
  • Response bhejne se pehle: Product list ka JSON gzip on; se compress hoke jaata hai (200KB → ~50KB) — slow mobile data pe bhi jaldi load.
  • Same product baar-baar maanga: "Top Deals" page ke liye har request DB tak jaati toh DB overload ho jaata — proxy_cache pehli request ka response 10 min save kar leta hai, agli 4999 requests seedha Nginx se, DB ko touch nahi karti.
  • Ek server slow ho gaya: proxy_buffering on; se Nginx poora response buffer kar leta hai, Node turant free ho jaata hai, user ke slow connection ka wait khud Nginx karta hai.
  • Ek backend crash: proxy_read_timeout 10s; se Nginx sirf 10 sec wait karke fail maan leta hai — bina timeout ke Nginx hamesha ke liye atakta, dheere-dheere saare workers busy ho jaate, poori site down lagti.
  • Profile photo upload (6MB): client_max_body_size default sirf 1MB — set na ho toh Nginx seedha 413 error deta, Node tak pahunchti hi nahi; isliye client_max_body_size 20M; set karte hain.

Poori picture: worker processes/connections ne bataya kitna traffic handle hoga → keepalive ne connections fast reuse kiye → gzip ne response chhota kiya → proxy caching ne DB bachaya → buffering ne backend jaldi free kiya → timeout ne crashed backend se pura system down hone se bachaya → client_max_body_size ne bada upload allow kiya.

Ab har term individually, point-by-point:

1. Worker Processes: Nginx start hote hi OS-level kuch worker processes spawn karta hai — asli traffic yehi handle karte hain (master process sirf inko manage karta hai). Har request ek worker sambhalta hai.

worker_processes auto;   # CPU cores jitne workers khud bana lo

Real use: auto almost hamesha best hai — har CPU core ko ek worker mil jaata hai, parallel traffic handle hoti hai; manually kam number dena underutilize karega.

2. Worker Connections: Har worker ek time pe kitne simultaneous connections khol sakta hai, uski limit:

events {
  worker_connections 1024;
}
# max clients ≈ worker_processes × worker_connections

Real use: High-traffic site (jaise 10k+ concurrent users) mein yeh value badhani padti hai, warna limit cross hote hi naye connections queue/reject hone lagte hain.

3. Keepalive: Normally har request ke liye naya TCP connection banta hai (handshake mein time lagta hai). Keepalive se ek connection reuse hota hai multiple requests ke liye — client↔Nginx aur Nginx↔backend, dono taraf set hota hai:

keepalive_timeout 65;         # client ke saath connection kitni der khula rahe

upstream backend_servers {
  server localhost:3001;
  keepalive 32;                # Nginx→backend, reusable connections ka pool
}

Real use: Bina keepalive ke, ek page ki 20 CSS/JS/image requests ke liye 20 alag TCP handshakes hote — keepalive se sab ek hi connection reuse karte hain, page fast load hota hai.

4. Buffering: Backend response ko Nginx pehle apne paas buffer karta hai, phir client ko bhejta hai (seedha stream nahi karta):

proxy_buffering on;
proxy_buffer_size 8k;
proxy_buffers 8 8k;

Real use: Slow client (weak internet) ho toh buffering se Node backend jaldi free ho jaata hai (Nginx baaki data client ko dheere-dheere bhejta rehta hai) — backend ka resource jyada der tak block nahi hota. Live streaming jaisi cheezon mein isko off karte hain.

5. Gzip: Response (HTML/CSS/JS/JSON) ko compress karke bhejta hai, browser use decompress kar leta hai — file size kaafi kam ho jaata hai:

gzip on;
gzip_types text/css application/javascript application/json;
gzip_min_length 1000;

Real use: 200KB ka JS bundle gzip se aksar 50-60KB tak aa jaata hai — slow network pe load time bahut kam ho jaata hai; sab production sites mein on hota hai.

6. Proxy Caching: Backend ka response Nginx khud apne paas save kar leta hai — same request dobara aaye toh backend tak jaaye hi na, seedha cache se reply:

proxy_cache_path /var/cache/nginx keys_zone=my_cache:10m;

location /api/products {
  proxy_cache my_cache;
  proxy_cache_valid 200 10m;   # 10 min tak cached response valid
  proxy_pass http://localhost:3000;
}

Real use: Product list jaisi kam-frequently-changing API — hazaron users same data maangte hain, bina caching Node/DB har baar query chalati, caching se DB load drastically kam ho jaata hai.

7. Timeouts: Backend response mein kitni der wait karna hai, uski limits — warna ek slow/hung backend Nginx ke resources bhi block kar dega:

proxy_connect_timeout 5s;   # backend se connect hone ka max wait
proxy_send_timeout 10s;     # backend ko request bhejne ka max wait
proxy_read_timeout 10s;     # backend se response aane ka max wait

Real use: Backend crash/hang ho jaaye toh bina timeout ke Nginx indefinitely wait karta rehta — saare connections busy ho jaate, poori site down lagne lagti; timeout hote hi Nginx turant client ko error de deta hai (graceful failure).

8. client_max_body_size: Client se aane wali request body (jaise file upload) ki max allowed size — default sirf 1MB hota hai:

http {
  client_max_body_size 20M;   # 20MB tak upload allow
}

Real use: User profile picture/PDF upload karta hai (5MB) aur yeh directive set nahi — Nginx 413 "Request Entity Too Large" error de deta hai, bhale Node/Express khud badi files accept karta ho. Isliye file-upload wale project mein yeh hamesha increase karna padta hai.

Ek line mein poora flow: worker_processes (kitne workers) × worker_connections (har worker ki capacity) = total handle-able traffic → keepalive se connections reuse hote hain → buffering se backend jaldi free hota hai → gzip se response chhota jaata hai → proxy caching se backend/DB par baar-baar hit nahi hota → timeouts se hung backend Nginx ko block nahi kar paata → aur client_max_body_size bina badhaye badi file uploads 413 error dete hain.

Phase 7 — Security

Poora Concept Ek Saath — Simple Flow

1. Rate Limiting: Ek IP se kitni requests/second allowed hain, uski limit — abuse/brute-force rokta hai:

limit_req_zone $binary_remote_addr zone=mylimit:10m rate=5r/s;

location /api/login {
  limit_req zone=mylimit burst=10 nodelay;
}

Real use: Bina iske koi bot login API pe second mein hazaron password try kar sakta hai (brute force). Rate limit lagte hi 6th request se hi 429 Too Many Requests milta hai.

2. IP Blocking: Specific IP/range ko allow ya deny karna:

location /admin/ {
  allow 203.0.113.10;   # sirf office IP
  deny all;             # baaki sab block
}

Real use: Admin panel sirf office/VPN IP se accessible rakhna, ya kisi known-malicious IP (repeated attack karne wale) ko permanently block karna.

3. Access Control: Sensitive paths/files ko public access se chhupana:

location ~ /\.(env|git) {
  deny all;
}
location /internal-docs/ {
  auth_basic "Restricted";
  auth_basic_user_file /etc/nginx/.htpasswd;   # username/password maangega
}

Real use: .env file (DB password, API keys) galti se public folder mein chhod di ho, toh deny na hone par koi bhi myshop.com/.env khol ke secrets padh sakta hai — isliye hidden/config files hamesha explicitly block karte hain.

4. Security Headers: Browser ko extra protection rules batane wale response headers:

add_header X-Frame-Options "SAMEORIGIN";           # iframe mein site load na ho (clickjacking)
add_header X-Content-Type-Options "nosniff";        # browser file type guess na kare
add_header Strict-Transport-Security "max-age=31536000"; # hamesha HTTPS use ho (HSTS)
add_header Content-Security-Policy "default-src 'self'"; # sirf apni site se script/style load ho

Real use: Bina X-Frame-Options ke, attacker myshop.com ko apni fake site pe invisible iframe mein load karke user se click karwa sakta hai (clickjacking) bina unhe pata chale.

5. CORS: Ek domain se chal rahi JS ko doosre domain (backend API) se data lene ki permission dena — browser by default isse block karta hai:

location /api/ {
  add_header Access-Control-Allow-Origin "https://myshop.com";
  add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE";
  add_header Access-Control-Allow-Headers "Content-Type, Authorization";
  proxy_pass http://localhost:3000/;
}

Real use: Frontend myshop.com aur backend API api.myshop.com alag domains hain — bina CORS headers ke browser console mein "blocked by CORS policy" error aata hai, request jaati hi nahi.

6. SSL Security (hardening): Sirf HTTPS lagana kaafi nahi — purane/weak encryption versions bhi band karne padte hain:

ssl_protocols TLSv1.2 TLSv1.3;      # purane TLS 1.0/1.1 band (weak/kamzor hain)
ssl_ciphers HIGH:!aNULL:!MD5;       # sirf strong encryption algorithms

Real use: Agar purane TLS versions allow rakhe, toh attacker downgrade attack karke connection ko jaan-boojh kar weak encryption pe force kar sakta hai aur data crack kar sakta hai — isliye sirf latest TLS versions allow karte hain.

7. DDoS Protection Basics: Ek saath hazaron fake requests bhejke server ko down karne ki koshish — poori tarah rokna mushkil hai, lekin Nginx level pe basic defense laga sakte hain, jo upar ke concepts ko hi combine karta hai:

limit_req_zone $binary_remote_addr zone=req_limit:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

server {
  limit_req zone=req_limit burst=20;
  limit_conn conn_limit 20;   # ek IP se max 20 open connections
}

Real use: rate limiting (requests/sec cap) + limit_conn (ek IP ke max connections cap) + timeouts (Phase 6) mil ke ek basic layer bana dete hain — bade DDoS ke liye alag se Cloudflare/AWS Shield jaisi service chahiye hoti hai, Nginx akela full protection nahi de sakta.

Ek line mein poora flow: Rate limiting se ek IP zyada requests nahi bhej sakta → IP blocking/access control se sensitive paths aur unwanted IPs door rehte hain → security headers se browser-level attacks (clickjacking, MIME-sniffing) rukte hain → CORS se sirf trusted frontend hi API use kar paata hai → SSL hardening se weak encryption band hoti hai → aur ye sab mil ke DDoS ke against ek basic defense layer banate hain.

P8

Phase 8 — Logs & Troubleshooting

Poora Concept Ek Saath — Simple Flow

1. Access Logs: Har successful request ka record — kaun (IP), kab, kaunsa URL, kaunsa status code, kitna time laga:

access_log /var/log/nginx/access.log;
203.0.113.5 - - [15/Sep/2026:10:22:31] "GET /api/products HTTP/1.1" 200 512 "-" "Mozilla/5.0..."

Real use: Kaunse pages sabse zyada hit ho rahe hain, kaunsa IP suspicious tarike se bahut zyada requests bhej raha hai — traffic analysis aur security dono ke liye.

2. Error Logs: Jab kuch galat ho — config issue, backend na milna, permission problem — uska record, alag file mein:

error_log /var/log/nginx/error.log warn;   # warn/error/crit level
2026/09/15 10:23:01 [error] connect() failed (111: Connection refused) while connecting to upstream, upstream: "http://127.0.0.1:3000/"

Real use: Site down hone par sabse pehle yahi file dekhte hain — access log mein sirf "kya hua" dikhta hai, error log mein "kyun fail hua" dikhta hai.

3. Log Format: Access log mein kaunsi fields chahiye, custom define kar sakte ho:

log_format custom '$remote_addr - $status "$request" $request_time s upstream:$upstream_response_time s';

access_log /var/log/nginx/access.log custom;

Real use: Default format mein response time nahi hota — performance debug karne ke liye $request_time/$upstream_response_time jaise fields custom format mein add karte hain, taaki pata chale slow request Nginx ki wajah se thi ya backend ki wajah se.

4. Common Error Status Codes: Interview mein sabse zyada poocha jaata hai — kaunsa code, kis wajah se aata hai:

CodeMatlabReal wajah
403 ForbiddenAccess denieddeny all; lagi hai, ya folder/file permissions galat hain, ya index.html hi missing hai aur directory listing off hai
404 Not FoundFile/route exist nahi kartaGalat URL, ya root path galat set hai, ya SPA mein try_files fallback missing hai
413 Payload Too LargeRequest body limit se badaclient_max_body_size (default 1MB) se badi file upload ki gayi
502 Bad GatewayBackend se invalid/no responseBackend server crash/down hai, ya galat port pe proxy_pass point kiya hai
504 Gateway TimeoutBackend ne time pe respond nahi kiyaBackend slow/hung hai, proxy_read_timeout se zyada der laga diya (jaise heavy DB query)

Real use: 502 vs 504 mein farak samajhna V.IMP hai — 502 matlab backend bilkul respond hi nahi kar raha (down/crashed), 504 matlab backend respond kar raha hai par bahut slow hai (timeout cross ho gaya). Dono alag fix maangte hain: 502 mein backend restart karo, 504 mein query/code optimize karo ya timeout badhao.

5. Nginx Troubleshooting (step-by-step): Site down/error aane par yeh order follow karo:

sudo nginx -t                              # 1. config syntax sahi hai?
sudo tail -f /var/log/nginx/error.log      # 2. live error dekho
sudo systemctl status nginx                # 3. Nginx khud chal raha hai?
curl http://localhost:3000                 # 4. backend seedha reachable hai?
sudo systemctl reload nginx                # 5. config change ke baad reload (restart nahi, zero-downtime)

Real use: nginx -t hamesha config edit karne ke baad chalao — galat syntax se seedha reload karoge toh Nginx crash ho sakta hai aur poori site down ho jaayegi; -t pehle hi error pakad leta hai bina kuch break kiye.

Ek line mein poora flow: Access log se pata chalta hai "kya" hua (kaun, kab, kaunsa URL) → error log se pata chalta hai "kyun" fail hua → custom log format se performance debug karne wali fields add karte hain → 403/404/413 client-side galtiyan hain (permission/missing/too-large), 502/504 backend-side problems (down vs slow) → aur troubleshoot karte waqt hamesha nginx -t → error.log → backend check → reload isi order mein jaate hain.

P9

Phase 9 — Production

Poora Concept Ek Saath — Simple Flow

1. Nginx + PM2: Node app ko seedha node server.js se chalana risky hai — crash ho gaya toh hamesha ke liye down reh jaata hai. PM2 ek process manager hai jo app ko alive rakhta hai, crash pe auto-restart karta hai, aur multiple instances (cluster mode) chala sakta hai; Nginx uske aage reverse proxy/load balancer ban ke baithta hai:

pm2 start server.js -i max --name myshop-api   # CPU cores jitne instances (cluster mode)
pm2 startup                                     # server reboot pe khud start ho jaaye
pm2 save

Real use: PM2 4 instances (3001-3004) chalata hai, Nginx upstream se unke beech load balance karta hai — ek instance crash ho, PM2 use turant restart kar deta hai, Nginx baaki 3 pe traffic bhejta rehta hai.

2. Nginx + AWS EC2: EC2 ek virtual server hai jahan Nginx + Node deploy karte hain:

sudo apt update && sudo apt install nginx -y
# Security Group mein inbound rules kholni padti hain:
# Port 80 (HTTP), Port 443 (HTTPS), Port 22 (SSH) — baaki sab band

Real use: Sabse common galti — Nginx install/config sab sahi hoti hai, lekin EC2 ke Security Group mein port 80/443 inbound allow nahi kiya hota — site bahar se open hi nahi hoti, jabki server pe sab thik chal raha hota hai.

3. Nginx + Jenkins (CI/CD): Jenkins automatically naya code pull → build → deploy karta hai, manually server pe jaake copy-paste nahi karna padta:

# Jenkins pipeline ka ek stage (deploy):
git pull origin main
npm install && npm run build         # React/Angular build
cp -r dist/* /var/www/myshop/dist/   # naye static files copy
pm2 reload myshop-api                # backend zero-downtime restart

Real use: Developer git push karta hai → Jenkins khud build+deploy kar deta hai 2-3 minute mein — bina iske, har deploy ke liye manually server pe SSH karke commands chalani padtin, slow aur error-prone.

4. Zero-Downtime Deployment: Naya code deploy karte waqt bhi users ko error/downtime nahi dikhna chahiye:

pm2 reload myshop-api   # ek-ek karke instances restart (rolling restart)
# restart NAHI — restart sab instances ek saath band-start karta hai (downtime hota)
# reload — ek instance restart hone tak baaki chalte rehte hain, phir agla

Real use: 4 PM2 instances hain — reload se ek-ek karke restart hote hain, kabhi bhi saare instances ek saath down nahi hote, isliye users ko koi error dikhta hi nahi.

5. Graceful Reload: Nginx config change karne ke baad bhi zero-downtime restart:

sudo nginx -t              # pehle syntax check (hamesha)
sudo nginx -s reload        # graceful — chal rahi requests complete hone dega
# 'systemctl restart nginx' NAHI — ye connections turant kaat deta hai

Real use: reload mein Nginx naya config load karta hai, naye worker processes spawn karta hai naye config ke saath, aur purane workers ko tab tak jeene deta hai jab tak unki existing requests complete na ho jaayein — koi request bich mein cut nahi hoti.

6. Production Configuration (checklist): Real project mein pichle saare phases ek saath combine hote hain:

server {
  listen 443 ssl;
  server_name myshop.com;
  ssl_certificate     /etc/letsencrypt/live/myshop.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/myshop.com/privkey.pem;

  root /var/www/myshop/dist;
  index index.html;
  client_max_body_size 20M;
  gzip on;

  location / { try_files $uri $uri/ /index.html; }
  location /api/ {
    proxy_pass http://backend_servers/;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_read_timeout 10s;
  }
}

Real use: Yeh ek hi file mein SSL (P3) + static/SPA (P5) + body-size/gzip (P6) + reverse proxy headers/timeout (P2/P6) — sab jud jaate hain. Interview mein aksar poocha jaata hai: "production config likho" — isi tarah ka combined answer expect hota hai.

7. Nginx Performance Tuning (final checklist): Production jaane se pehle yeh sab verify karo:

SettingKyun
worker_processes auto;Sab CPU cores use ho
gzip on;Response size chhota
keepalive (client + upstream)Connection reuse, less handshakes
proxy_cacheRepeated requests backend/DB tak na jaayein
expires/Cache-ControlStatic assets browser-cached rahein
Timeouts setHung backend Nginx ko block na kare

Real use: Yeh checklist Phase 6 (Performance) ka hi production-ready summary hai — deploy se pehle ek-ek karke confirm karte hain ki sab lagaya gaya hai.

Ek line mein poora flow: PM2 Node app ko alive rakhta hai (cluster mode) → EC2 pe deploy karte waqt security group ports khulwana mat bhoolo → Jenkins build+deploy automate karta hai → deploy karte waqt PM2 reload (backend) + Nginx graceful reload (config) se zero-downtime milta hai → aur production config mein pichle saare phases (SSL, static, proxy, performance) ek saath combine hote hain.

Nginx basics — web server, reverse proxy aur load balancer ke fundamentals, interview-prep format mein. Progress aur learned-status is browser mein locally save hota hai.
